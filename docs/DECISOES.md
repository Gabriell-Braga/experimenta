# Decisões

Formato: contexto, opções, escolha, motivo.

## D-001 — Postgres sem Docker no ambiente de desenvolvimento
- Contexto: o plano pede docker-compose para o Postgres, mas a máquina de desenvolvimento atual não tem Docker instalado.
- Opções: (a) bloquear até instalarem Docker; (b) exigir Postgres nativo; (c) manter docker-compose.yml para quem tem Docker e usar PGlite (Postgres compilado para WASM, mesmo dialeto SQL) como fallback embutido quando `DATABASE_URL` não estiver definida.
- Escolha: (c).
- Motivo: Drizzle suporta os dois drivers com o mesmo schema; testes e `pnpm dev` funcionam sem infraestrutura externa; produção continua em Postgres real.

## D-002 — pnpm instalado via npm global
- Contexto: `corepack enable` falhou com EPERM em `C:\Program Files\nodejs`.
- Escolha: `npm i -g pnpm@9`. Versão fixada em `packageManager` no package.json raiz.

## D-003 — Pesquisa: premissas vs VWO/Optimizely (2026-10-14)
Fontes: help.vwo.com (artigos 360037883434, 360020440754, 900001789546), speedcurve.com/blog/web-performance-anti-flicker-snippets, docs da Adobe Target (Flicker Management), docs de extensões de Builder.io, Adobe Visual Editing Helper, Webtrends Optimize, Mida.
- **Confirmado — anti-flicker do VWO esconde a página inteira:** o SmartCode async esconde o `body` (campo `hide_element`), com `settings_tolerance` 2000 ms e `library_tolerance` 2500 ms. No timeout mostra o original e não rastreia. Nosso anti-flicker por elemento + timeout 1500 ms é diferencial real.
- **Diverge parcialmente — "por elemento" não é inédito:** Adobe Target (Flicker Management V2) pré-esconde só seletores extraídos das atividades. Continua sendo diferencial frente a VWO/Optimizely, não frente a todo o mercado.
- **Confirmado — extensão para iframe bloqueado:** padrão de mercado (Adobe Visual Editing Helper, Builder.io, Webtrends, Mida) remove X-Frame-Options e CSP frame-ancestors. Adobe e Builder.io também ajustam `SameSite` dos cookies para o login do site funcionar dentro do iframe. **Adição ao plano:** a extensão (5.1) também reescreverá `SameSite=None; Secure` em Set-Cookie apenas nas sessões de edição, senão sites com login quebram no iframe. Builder.io limita a reescrita ao contexto do próprio app, mesma ideia do nosso "só sessões iniciadas pelo app".
- **Confirmado — snippet síncrono no `<head>`:** recomendação de VWO e Optimizely para reduzir flicker. Nosso snippet deve ser instalado como primeiro script do head; o `<style>` anti-flicker é injetado de forma síncrona.
- **Não verificado:** documentação oficial do Optimizely sobre timeout padrão (fontes de terceiros divergem: 1–3 s). Não afeta o plano.

## D-004 — Contrato em packages/shared
- Operações: união discriminada por `type`; `move` e `insertHTML` usam `position` before/after/prepend/append (prepend/append = "dentro"). `move.value.anchor` é um Target completo (também cura).
- Experimento referenciado por `key` legível (usado em `ab_force=chave:variacao`) e `id` interno; a primeira variação é o controle; pesos inteiros relativos.
- Snippet só faz `import type` de shared (zod fica fora do bundle de 10 KB). A validação forte acontece na API e no editor; o snippet confia no JSON publicado.
- Eventos de tracking têm `eventId` para deduplicação no analytics.

## D-005 — Resolução de alvo
- Cada operação age sobre UM elemento (o primeiro que casa). Motivo: a impressão digital e a cura só fazem sentido para um elemento; mudanças em listas usam customCSS ou uma operação por item.
- Cura por impressão digital: varre elementos da mesma tag, pontua texto exato (+3), texto parcial (+1), atributos (id/data-* +2, demais +1), posição (<50 px +1, <200 px +0,5). Aceita só com pontuação ≥ 3 e vantagem ≥ 1 sobre o 2º colocado (evita curar para o elemento errado).
- O seletor curado relatado no evento é um caminho nth-of-type curto (ancorado em id), gerado no próprio snippet — o gerador completo fica fora do bundle.

## D-006 — Motor de operações (packages/snippet/src/engine)
- Fica no pacote do snippet (export `@abtest/snippet/engine`) porque é o código de runtime; o agent importa o mesmo motor para pré-visualizar ao vivo — uma única implementação.
- Cada aplicação devolve `undo`; `ApplyHandle.revert()` desfaz tudo em ordem inversa. O editor usa isso para trocar de variação e desfazer sem recarregar a página.
- `setStyle`/`hide` usam `!important` inline para vencer o CSS do site. `hide` = `display:none`; `remove` remove o nó de fato.
- O timeout de espera por elementos conta a partir do DOMContentLoaded (o snippet roda no `<head>`, antes do body existir).
- O observer é desconectado enquanto aplicamos, para nossas próprias mutações não dispararem nova rodada.

## D-007 — Modo `persist` no motor
- Contexto: em SPAs (React/Vue), re-render pode substituir o nó alvo depois da aplicação, apagando a variação.
- Escolha: opção `persist` mantém o MutationObserver ativo e aplica a operação em qualquer nó novo que o alvo resolva (WeakSet evita reaplicar no mesmo nó). O snippet usa `persist: true`; para ao trocar de rota/variação.
- Limitação conhecida: se o framework alterar o conteúdo do MESMO nó (sem trocá-lo), a operação não é reaplicada.

## D-008 — Configuração embutida no JS da conta (estilo Optimizely)
- Contexto: anti-flicker por elemento exige conhecer os seletores ANTES do primeiro paint. Buscar um JSON via fetch é assíncrono — no primeiro acesso não daria para esconder só os elementos, teríamos de esconder a página (o que o VWO faz).
- Opções: (a) snippet genérico + fetch do JSON (esconde página até chegar); (b) XHR síncrono (obsoleto, bloqueia); (c) publicar `/cdn/<conta>.js` = `window.__ABT_CONFIG__ = {...};` + runtime, carregado com um único `<script>` síncrono no `<head>`.
- Escolha: (c). A publicação grava também `/cdn/<conta>.json` (contrato para integração/analytics).
- Cache: o arquivo é servido com `Cache-Control: max-age=60` + ETag; publicar sobrescreve o arquivo e incrementa `version` (numa CDN real, publicar dispara purge do caminho).
- Instalação no site: `<script src="https://<cdn>/cdn/<conta>.js"></script>` como primeiro script do `<head>`.
- Limite de 10 KB gzip vale para o runtime; a config embutida é medida à parte.

## D-009 — Bucketing
- Um único hash: `b = murmurhash3(visitorId + experimentId) % 10000`. Entra se `b < traffic × 100`; dentro dessa faixa, `b / faixa × somaPesos` escolhe a variação. Determinístico e independente entre experimentos (o id entra no hash).
- Persistência em localStorage `_abt_a` (experimentId → variationId). Visitante fora do tráfego não é persistido: se o tráfego aumentar, pode entrar depois; quem já entrou mantém a variação mesmo com mudança de pesos. Variação removida → nova atribuição.
- Bots por User-Agent são ignorados (não entram em experimento nem geram eventos). HeadlessChrome não é tratado como bot (testes E2E).

## D-010 — Anti-flicker e teste por frames
- CSS: uma regra por seletor `:is(<sel>):not([data-abt-ok]){visibility:hidden!important}`; ao aplicar a operação o elemento recebe `data-abt-ok` e reaparece. `:is()` isola listas de seletores; regra por seletor evita que um seletor inválido anule os demais. Modo página: `html{opacity:0!important}`.
- Timeout de segurança conta do início do snippet (padrão 1500 ms); no fim (tudo aplicado ou timeout) o `<style>` é removido.
- Teste E2E: (1) script de init amostra em cada requestAnimationFrame a visibilidade/conteúdo dos elementos; (2) CDP `Page.startScreencast` captura os frames realmente pintados (PNG) e o teste conta pixels da cor original do botão na região dele — deve ser zero em todos os frames. Há um controle negativo que prova que a amostragem detecta flicker.
- Variação de controle (sem operações) não esconde nada.

## D-011 — SPA
- `history.pushState`/`replaceState` são envolvidos e `popstate` é ouvido; a cada mudança real de URL o runtime reavalia: experimentos que deixaram de casar são revertidos (`revert` do motor + remoção de customCSS), os novos são ativados (com anti-flicker por elemento), os que continuam ativos seguem com o observer `persist`.
- `exposure` é emitido a cada ativação (primeira carga ou reentrada na rota segmentada), não a cada navegação.

## D-012 — Eventos, metas e QA
- Transporte: sendBeacon com `text/plain` (sem preflight CORS), lote a cada 1 s, flush imediato em conversão e no pagehide/visibilitychange. Conversão envia na hora porque costuma preceder navegação (beacons disparados durante o unload são menos confiáveis).
- Conversões são atribuídas a todos os experimentos em que o visitante está (atribuições persistidas), não só aos ativos na página — a meta costuma estar em outra URL.
- Modo QA (`?ab_force=exp:var`) ignora segmentação/tráfego, não persiste atribuição, fica salvo na sessão (`?ab_force=off` limpa) e marca eventos com `qa: true` em vez de suprimi-los (o analytics filtra; facilita depurar a integração).
- Integração sem código: `CustomEvent('abt:event')` no window e adaptadores via `abq.push(['adapter', fn])`.

## D-013 — Protocolo RPC app ↔ agent
- Envelope `{abt:1, kind:'req'|'res'|'evt'}` sobre postMessage; os dois lados podem chamar métodos e emitir eventos (`createPeer`).
- Segurança: `origin` exato obrigatório (nunca `'*'`), usado como targetOrigin no envio e conferido junto com `event.source` em toda mensagem recebida. Parâmetros, resultados e eventos são validados com zod; mensagens inválidas são ignoradas.
- Contrato em `packages/shared/src/rpc.ts`: agent expõe `ping`, `setMode`, `applyVariation` (sempre a lista COMPLETA de operações: o agent reverte e reaplica, simples e sem estado divergente), `select`, `highlight`; app expõe `prompt` (pedir HTML/URL de imagem ao usuário); agent emite `ready`, `selected`, `operation` (rascunho sem id/ordem — o app numera), `navigated`.

## D-014 — Handshake do modo edição
- Três condições (plano): `?abt_edit=<token>` + token validado na API (emitido para a mesma conta; a API devolve o `appOrigin` que criou a sessão) + handshake postMessage com origin exato. O origin do app NUNCA vem da URL (um atacante poderia apontar para o próprio domínio) — vem da sessão na API.
- O `hello` do snippet usa targetOrigin = appOrigin: uma página maliciosa que emoldure o site com um token roubado nem recebe a mensagem. O `hello-ack` precisa vir de `window.parent`, do appOrigin e ecoar o token.
- Só dentro de iframe (`parent !== window`); o token fica no sessionStorage do iframe (particionado pelo site de topo no Chrome) para sobreviver à navegação no modo "navegar".
- Sessões em memória na API (ponytail: mover para banco/Redis com múltiplas instâncias). Criação restrita por CORS + checagem do header Origin contra `EDITOR_ORIGINS`; autenticação de usuário entra na 4.2.
- O agent é carregado da mesma pasta do script da conta (`new URL('agent.js', currentScript.src)`), sem config extra.

## D-015 — Agent: overlay e captura de eventos
- UI do agent num custom element `<abt-editor-overlay>` filho de `<html>` (fora do body, não entra nos caminhos nth-of-type), com Shadow DOM e `:host{all:initial}`; caixas com `pointer-events:none`, só o breadcrumb recebe cliques.
- No modo edição, listeners em captura no window bloqueiam click/mousedown/pointer/submit/dblclick/contextmenu do site (`stopImmediatePropagation`) — o site não navega nem reage. Eventos vindos do overlay (`composedPath`) passam.
- Navegação no modo "navegar" recarrega a página no iframe; o snippet refaz o handshake e o agent emite `ready` de novo — o app trata `ready` como (re)conexão e reenvia modo + variação.
- Seletor sugerido segue a prioridade do pacote selector (atributos semânticos como `href` vêm antes de classes).

## D-016 — Interações de edição no agent
- O agent nunca altera o DOM de forma definitiva: edição inline, arrastar e menu de contexto geram RASCUNHOS de operação (`operation`); o app numera, guarda e chama `applyVariation` com a lista completa. Ao confirmar a edição inline o agent restaura o original — a mudança volta pela variação. Fonte única da verdade = lista de operações no app (desfazer/refazer triviais).
- Edição inline: duplo clique → `contenteditable`; Enter/blur confirma, Shift+Enter quebra linha, Esc cancela. Sem filhos elemento → `setText`; com filhos → `setHTML`.
- Arrastar: alça (⠿) ao lado do rótulo do selecionado; usa pointer events + `elementsFromPoint`; faixa superior 25% = antes, inferior 25% = depois, meio = dentro (exceto elementos vazios/void). Listeners de arraste registrados antes do bloqueio de eventos (que usa stopImmediatePropagation).
- Inserir HTML e trocar imagem pedem o valor ao app via RPC `prompt` (o diálogo fica fora do iframe).

## D-017 — App do editor
- Estado com `useReducer` puro (testável sem React) em vez de lib de estado: experimento, variação ativa, histórico (100 passos) com desfazer/refazer; trocar de aba não entra no histórico.
- Modos: Editar (agent intercepta), Navegar (site interativo, variação aplicada, navegação real no iframe com reconexão automática), Preview (como Navegar, sem painéis e com faixa indicando a variação). "Preview" não abre nova aba com `?ab_force` porque o rascunho ainda não está publicado.
- Dispositivo = largura do iframe (100% / 768 px / 390 px). O User-Agent não muda — segmentação por dispositivo depende de UA e não é simulada no editor.
- Salvar grava em localStorage até a fase 4 (API). Ctrl+Z / Ctrl+Shift+Z / Ctrl+S no app.

## D-018 — Painel de propriedades
- Cada elemento tem no máximo UMA operação `setStyle` (as propriedades fazem merge), uma `setText` e uma `setAttribute` por nome — `upsertOperation` no store localiza a equivalente (mesmo seletor + tipo [+ nome do atributo]). Mantém a lista de alterações curta e legível.
- Campos de texto confirmam no Enter/blur (uma operação por edição, não por tecla). O seletor de cor usa `coalesceKey`: arrastar no picker gera uma única entrada no histórico.
- Valor exibido = valor da variação, se houver; senão o estilo computado enviado pelo agent na seleção. Borda é editada pelos atalhos `border-width/style/color` (exibe o lado superior).
- Indicador de fragilidade (estável/médio/frágil) já aparece no painel (base para 6.2).

## D-019 — Lista de alterações e código custom
- Barra lateral com abas Elemento / Alterações / CSS-JS. A lista mostra cada operação em ordem de aplicação com descrição legível, destaca o alvo no site ao passar o mouse (`highlight`), seleciona ao clicar, reordena (↑/↓) e exclui. Operações que não acharam o elemento na página atual ficam em vermelho e a aba mostra ⚠N (base do "alerta quando uma alteração não encontra o elemento"); curadas por alternativo/impressão digital ficam em amarelo.
- Monaco empacotado localmente (`monaco-editor` + workers via `?worker` do Vite, sem CDN) e carregado sob demanda (`React.lazy`) — o chunk é grande, mas só baixa ao abrir a aba de código.
- customCSS aplica ao vivo. customJS só executa no editor quando o usuário marca "Executar o JS no editor" (roda na página real do cliente). A permissão de PUBLICAR customJS fica na API (4.2).

## D-020 — Modelo de dados
- Tabelas: accounts, users (role owner/editor/viewer + `can_publish_js`, senha scrypt), projects (site), experiments (segmentação/anti-flicker em jsonb), variations (operações em jsonb — lista de operações, nunca HTML), goals (definição jsonb validada pelo zod), experiment_versions (snapshot completo a cada salvamento), publications (config publicada, só inserção).
- `account_id` em todas as tabelas de tenant, com índice; chave do experimento única POR CONTA. O repositório não expõe nenhuma consulta de tenant sem `accountId`; tentativa de gravar id de experimento de outra conta ou em projeto de outra conta → NotFoundError (não revela existência).
- Salvar = substituir variações e metas do experimento numa transação (simples; o volume por experimento é pequeno) + nova versão.
- Migrações versionadas com drizzle-kit e aplicadas no start (`migrate`), mesma pasta para PGlite e Postgres.

## D-021 — API, autenticação e permissões
- `@hono/zod-openapi`: as rotas são declaradas com os MESMOS schemas zod de `packages/shared` → validação e OpenAPI 3.1 (`/openapi.json`, Swagger em `/docs`) sem duplicar contrato.
- Autenticação por JWT HS256 (12 h) emitido em `/auth/login` (senha scrypt). O middleware recarrega o usuário do banco a cada requisição (papel atualizado, usuário removido perde acesso) e a conta vem do token — nunca do corpo. Login social/SSO e refresh token ficam para depois.
- Papéis: viewer (lê), editor (cria/salva/abre sessão de edição/publica), owner (tudo). Publicar customJS exige owner ou `can_publish_js` (checado na publicação, 4.3). Recursos de outra conta respondem 404 (não revelam existência).
- CORS: rotas privadas só aceitam os origins do editor (`EDITOR_ORIGINS`); `/cdn/*`, `GET /edit-sessions/:token` e coleta de eventos são públicas.
- O editor deixa de usar localStorage para o experimento: login → lista → `?exp=<id>`; salvar = PUT (nova versão). Seed de desenvolvimento com conta `demo` e um usuário de cada papel.

## D-022 — Publicação e coleta
- `POST /publish` (editor+) compila os experimentos com status `running` da conta num `PublishedConfig` versionado (última versão + 1), registra em `publications` (só inserção — histórico imutável) e grava `/cdn/<conta>.json` e `/cdn/<conta>.js`. Publicar = sobrescrever os arquivos (numa CDN real: + purge do caminho).
- Regra do customJS: sem permissão (`owner` ou `can_publish_js`), a publicação é recusada (403) se algum customJS em execução for NOVO ou DIFERENTE do que já está publicado; republicar JS idêntico (aprovado antes) é permitido, para editores poderem publicar outras mudanças.
- `POST /collect` público (CORS `*`, text/plain, até 64 KB e 200 eventos por lote): valida cada evento com o schema, ignora inválidos e contas inexistentes, deduplica por `eventId` (`ON CONFLICT DO NOTHING`), guarda em `events` para o painel de saúde. Responde 204 sem detalhes. Sem rate limit (ponytail).

## D-023 — Configurações e publicação no editor
- Aba "Config": nome, status, tráfego (%), pesos por variação (mostra %), regras de URL (é/contém/regex + excluir) e metas (clique, visita a URL, formulário, evento custom; chave gerada do nome). Tudo passa pelo reducer (desfazer/refazer).
- "Publicar" salva o experimento e publica a CONTA inteira (a config por conta é um arquivo só). Se o experimento atual não está "Em execução", o aviso diz que ele não entra na publicação.
- E2E usa a CDN real da API (`e2e/.cdn`, limpa a cada execução por `e2e/reset-cdn.mjs`) — o visitante do teste carrega snippet + config exatamente como em produção.

## D-024 — Extensão Chrome MV3
- Ponte: content script `bridge.js` injetado SÓ nos origins do editor (manifest gerado com `EDITOR_ORIGINS`) faz window.postMessage ↔ service worker. O app não precisa saber o ID da extensão e nenhuma outra página consegue abrir sessão (o SW só aceita `start` do frame principal de uma aba onde a ponte rodou).
- Regras `declarativeNetRequest.updateSessionRules` por sessão: condição `tabIds:[aba do editor]` + `resourceTypes:['sub_frame']` + regex do origin exato do site; ação remove `X-Frame-Options`, `Content-Security-Policy` e `-Report-Only` (DNR não edita diretivas). Nada muda na navegação normal do usuário nem em outras abas. Sessão expira em 15 min, fecha com a aba ou quando o editor sai (`end`). Estado em `chrome.storage.session` (o SW pode morrer).
- Injeção: content script em todos os frames só age dentro de iframe com `abt_edit` E se o SW confirmar sessão para aquela aba+origin. Se o site não tem o snippet (marca `data-abt-editor` ausente), injeta o script da conta (`<apiUrl>/cdn/<conta>.js`), que faz o handshake normal (token na API + origin exato) e carrega o agent — mesma segurança do caminho com snippet.
- Editor: se o snippet não responder em 5 s, tenta a extensão automaticamente (ping → start → recarrega o iframe); sem extensão, mostra aviso para instalar.
- **Diverge de D-003:** `SameSite` de cookies NÃO é reescrito — DNR só consegue remover/definir o header `Set-Cookie` inteiro, não seus atributos. Sites com login em cookie `SameSite=Lax/Strict` podem não manter a sessão dentro do iframe. Alternativa futura: `chrome.cookies` para reescrever os cookies do domínio durante a sessão (exige permissão `cookies`).

## D-025 — Saúde dos seletores
- `GET /experiments/{id}/health` agrega a tabela `events` (filtrada por conta e experimento): exposições por variação e, por operação, contagem de `selector_failed`/`selector_healed`, último seletor curado (+via) e última ocorrência — uma consulta SQL com `count(*) filter` e `array_agg ... order by ts desc`.
- Editor, aba "Saúde": por alteração da variação ativa mostra OK / falhou N× (taxa sobre exposições) / curado N× com o seletor usado. "Adotar este seletor" troca o seletor principal pelo curado e rebaixa o antigo para alternativo (mantém a cura possível se o site voltar atrás). Depois é preciso salvar e publicar.

## D-026 — Aviso de seletor frágil
- `selectorFragility(selector)` (packages/selector) avalia qualquer seletor só pelo texto (inclusive os editados/adotados): `high` se usa nth-* ou id/classe com cara de gerada; `low` se ancorado num id/data-* estável sem combinadores ou classe estável simples; `medium` no resto.
- Três pontos de aviso no editor: dica no painel ao selecionar elemento frágil, faixa amarela ao criar uma alteração frágil (com sugestão de pedir `data-testid`) e ⚠ na lista de alterações. Não bloqueia: a impressão digital ainda tenta curar.

## D-027 — Conflito entre experimentos
- `GET /experiments/{id}/conflicts` (apps/api/src/conflicts.ts): outros experimentos não arquivados da conta que alteram o mesmo elemento — compara seletor principal + alternativos normalizados (espaços nos combinadores) de todas as variações.
- Sobreposição de páginas aproximada: a página de referência (editorUrl) de um casa com a segmentação de URL do outro, em qualquer sentido (regras vazias = todas), e os dispositivos não são disjuntos. Não tenta provar interseção de regex — falso positivo é aceitável (é aviso), falso negativo raro.
- Editor: faixa ⚔ na aba Alterações + marca por alteração; ao Publicar, avisa se o conflito é com experimento em execução. Não bloqueia (às vezes é intencional, ex.: experimentos mutuamente exclusivos por segmentação de público que a heurística não enxerga).

## D-028 — Versões e restauração
- Toda gravação já gera um snapshot completo (D-020). Restaurar = gravar o snapshot escolhido como NOVA versão (v1 → restaurada como v3): o histórico é append-only, dá para "desfazer a restauração" restaurando a v2.
- `GET /experiments/{id}/versions/{v}` devolve o snapshot; `POST .../restore` exige editor. Restaurar não publica — publicar continua sendo ação explícita.
- Editor: aba "Versões" com confirmação em dois cliques (sem diálogo nativo) e aviso de alterações não salvas; após restaurar recarrega o experimento.

## D-029 — Captura para mapa de calor (snippet)
- Ligado pela config publicada (`heatmap.sampleRate`; hoje global via `HEATMAP_SAMPLE_RATE`, padrão 1 em dev). Amostragem determinística por visitante (`murmurhash3(visitorId + ':heatmap')`), nunca em modo QA.
- Clique: seletor curto do elemento clicado (`pathOf`, ancorado no id mais próximo) + posição RELATIVA dentro do elemento (rx, ry 0..1) + coordenadas de página e viewport. Desenhar pela posição relativa ao elemento sobrevive a layouts responsivos e conteúdo dinâmico (melhor que só px/py).
- Scroll: profundidade máxima (% da altura da página), um evento por página vista — no `pagehide` e a cada navegação de SPA (com a URL antiga); força flush do lote.
- Cada evento leva `device` e `variations` (experimentos ATIVOS na página → variação) para filtrar o mapa por variação e dispositivo. Mesmo transporte (lote/sendBeacon) e endpoint `/collect`; o schema `TrackingEventSchema` ganhou os tipos `click` e `scroll` (`HeatmapEvent`).
- Runtime: 7,2 KB gzip.

## D-030 — Agregação do mapa de calor
- `GET /heatmap` agrega direto da tabela `events` em SQL (normaliza a URL em SQL igual ao `normalizePage` do Node), cliques por seletor com até 200 pontos (os mais recentes) por elemento, e alcance de scroll em faixas de 10%. - Contexto: pedido de colocar tudo online na Cloudflare; sem Docker na máquina e sem Postgres gerenciado disponível na conta (Hyperdrive exigiria um Postgres externo).

## D-035 — Performance em produção e UX do app (pós-plano)

## D-037 — Reaplicação em modo persist e configurações fora da edição
- Bug: no modo `persist` (snippet e agent) cada mutação do DOM re-resolvia todos os seletores e aplicava a operação em qualquer elemento ainda não processado. Seletores por posição/classe passam a casar com nós inseridos ou movidos pela própria variação: `insertHTML` antes do alvo duplicava o bloco, `remove` removia em cadeia, `move` movia o vizinho e o elemento "não ficava".

Só re-resolve quando o elemento sai da página (re-render do framework). `remove` tira o próprio alvo: só reaplica se o elemento novo tiver o mesmo `outerHTML` do removido (re-render idêntico).
- Edição inline/“Editar HTML” capturam o innerHTML sem os nós `data-abt-inserted` (copiá-los gerava a duplicação na própria setHTML).
- Configurações (status, tráfego, pesos, páginas, metas) viraram janela própria aberta pela barra superior: separadas da edição visual, como pedido. A meta de clique/formulário pode ser escolhida clicando no site (o próximo elemento selecionado preenche o seletor).

## D-042 — Motor estatístico (fase 9.3)
- Bayesiano como padrão da interface (como o SmartStats do VWO): taxa de conversão com posterior Beta(1+conv, 1+não-conv) e receita por visitante com posterior Normal(média, s²/n). Probabilidade de vencer o controle, de ser a melhor, perda esperada e intervalos de 95% saem de 20 mil amostras Monte Carlo com PRNG de semente fixa — mesmo dado, mesmo número na tela (sem "pular" a cada recarga). Validado contra a fórmula exata de P(B>A) para Beta.
- Frequentista ao lado (z-test de proporções e Welch para médias) para quem pede p-valor; SRM por qui-quadrado (p < 0,01 = alerta de divisão de tráfego quebrada); tamanho de amostra pela aproximação normal (α 5%, poder 80%).
- Veredito da UI: vencedora ≥ 95% de chance de bater o controle (com mínimo de visitantes), perdedora ≤ 5%, "liderando" ≥ 75%. Sem dependências: o mesmo código roda na API e no editor (`@abtest/shared/stats`).

## D-043 — Relatório do experimento (fase 9.4)
- Visitante do relatório = quem recebeu `exposure` (contado uma vez, na primeira variação vista). Conversão = visitante único que converteu a meta DEPOIS de exposto; receita = soma dos valores (conversões repetidas somam receita, não visitantes). Eventos de QA ficam fora.
- Meta primária = primeira meta da lista (sem coluna nova): "Tornar primária" nas Configurações move a meta para o topo. Ela decide a manchete, a série acumulada e a estimativa de duração.
- Filtro de dispositivo: as exposições não carregam dispositivo; usa-se o dispositivo predominante das páginas vistas de cada visitante exposto (pageviews são coletados de todos, D-041).
- Duração estimada: amostra para detectar +10% sobre a taxa atual do controle ÷ ritmo médio diário de visitantes.
- `pnpm seed:data` gera tráfego realista para a conta demo (dev) pelo próprio `/collect` — os módulos de insights vão estender o gerador.

## D-046 — Gravação de sessão (fase 10.3)
- rrweb (`@rrweb/record` 2.1.7, MIT) em vez de gravador próprio: serializar DOM + mutações + estilos com fidelidade é o problema inteiro e o rrweb é o padrão de mercado (PostHog, Highlight). Fica num bundle à parte, `insights.js` (~24 KB gzip), carregado de forma assíncrona só para visitantes amostrados — o runtime principal segue < 10 KB (8,5 KB).
- Transporte próprio (`POST /rec`) em vez do `/collect`: blocos são grandes (snapshot completo) e não cabem no limite de 64 KB do beacon nem no schema de eventos. Blocos > 900 KB são divididos ao meio no navegador; ao sair da página usa `keepalive` quando o corpo cabe (< 60 KB), senão o resto daquela página se perde (aceito).
- Armazenamento: `recordings` (metadados por sessão: início/fim, páginas em ordem pelos eventos Meta, dispositivo, viewport, nº de eventos) + `recording_chunks` (JSON dos eventos). As duas implementações (Postgres e D1) seguem o mesmo contrato. Retenção junto com os eventos crus.
- Privacidade por padrão: `maskAllInputs`, classes `abt-block`/`abt-mask` para o time do site esconder trechos.
- ponytail: metadados atualizados por leitura+escrita (sem lock): dois blocos simultâneos da mesma sessão podem perder uma página da lista; os eventos não se perdem.

## D-052 — Tipos de campanha (fase 12.1)

## D-053 — Teste multivariado (fase 12.2)
- MVT fatorial completo: `sections[]` (cada uma com opções; a 1ª é o original) e as variações são as combinações geradas por `mvtVariations` (produto cartesiano; combinação só com originais = controle). Combinações existentes mantêm id/chave/peso ao regenerar (atribuição persistida dos visitantes não muda). No site, nada muda no snippet: cada combinação é uma variação comum com as operações/CSS das opções juntados.
- No editor, as abas de variação viram seções × opções; a edição vai para a OPÇÃO ativa (uma "variação" virtual memoizada por objeto de opção) e as combinações são refeitas a cada mudança (desfazer/refazer incluídos). JS custom por opção não é suportado (só operações e CSS).
- Relatório: além da tabela por combinação, "efeito por seção" soma visitantes/conversões de todas as combinações que contêm cada opção e compara com o original da seção (efeito principal, como no VWO).
- ponytail: fatorial completo cresce rápido (3 seções × 3 opções = 27 combinações, tráfego dividido por 27). Fatorial fracionado/Taguchi fica para quando alguém precisar.

## D-054 — Multi-armed bandit (fase 12.3)
- `allocation: 'bandit'`: de hora em hora (Node: `setInterval`; Worker: cron `0 * * * *`) os pesos das variações em execução são recalculados pela meta primária nos últimos 30 dias: Thompson sampling (probabilidade de cada braço ser o melhor, mesmo Monte Carlo do motor estatístico) com piso de exploração de 5% por braço; sem 100 visitantes no total, divisão igual. Muda só a divisão de visitantes NOVOS (a atribuição de quem já entrou é persistida) — como nos bandits web do VWO.
- Mudou → nova versão do experimento + republicação da conta com um usuário de sistema SEM permissão de JS: se houver customJS novo que ainda não foi publicado por quem pode, a publicação automática é recusada e os pesos ficam só salvos (não contorna a regra de permissão).
- "Rebalancear agora" no relatório chama `POST /experiments/{id}/rebalance`.

## D-055 — Audiências e captura de insights fora do runtime (fase 13.1)
- Audiência = entidade `audience` (`match` all/any + regras). Avaliada no navegador, sem ida ao servidor (sem atraso nem flicker): regras de comportamento usam o perfil local (páginas vistas, sessões, eventos, caminhos visitados, origem first-touch), além de referrer, UTM, atributos (`identify`/`set`), cookie, variável JS, idioma, horário/dia, dispositivo, novo/recorrente e score preditivo (15.3). O perfil é atualizado ANTES de avaliar (a página atual conta). `identify`/`set` reavaliam na hora.
- A publicação leva só as audiências usadas por experimentos publicados. Audiência ausente (excluída depois) = ninguém entra (mais seguro que liberar para todos); a interface avisa.
- Geolocalização por IP ficou de fora: a config é estática por conta (CDN) e não conhece o IP do visitante.
- Espaço no snippet: a captura de mapa de calor/frustração/movimento saiu do runtime para o `insights.js` (carregado só para amostrados). Runtime com audiências: 8,5 KB gzip (era 9,3 KB antes da mudança). Custo: cliques nos primeiros milissegundos antes do insights.js carregar não entram no mapa de calor (aceito).

## D-056 — Conteúdo dinâmico (fase 13.2)
- Tokens `{{fonte.chave|padrão}}` em setText/setHTML/insertHTML/setAttribute, resolvidos no navegador na ativação: `attr` (atributos do visitante), `query` (URL), `utm` (URL ou 1ª visita), `cookie`, `js` (variável global com pontos).
- Segurança: parâmetros de URL são controlados por quem envia o link. Em HTML o valor vira entidades; em atributos de URL (`href`, `src`, `action`…) vai com `encodeURIComponent` (bloqueia `javascript:`); atributos de evento (`on*`) nunca recebem dados; em texto (`textContent`) não há risco.
- O editor mostra o token cru (o visitante real é que tem os dados); dica de uso no painel de texto.

## D-057 — Pop-ups, barras e gatilhos (fase 13.3)
- Entidade `popup` (formato modal/slide-in/barra topo/rodapé, título, texto, CTA, cupom copiável, imagem, tema, cor), com gatilho (carregamento, atraso, scroll %, intenção de saída — mouse saindo pelo topo no desktop, subida rápida no celular —, inatividade, clique em seletor), frequência (uma vez, por visita, sempre) e segmentação (páginas, dispositivos, audiências). Publicação leva os em execução para `config.popups`.
- `engage.js` (bundle sob demanda, ~3,7 KB gzip, mesma pasta do script da conta) só é carregado quando há campanha publicada. Renderiza em Shadow DOM (CSS do site não interfere), textos por `textContent` (nunca HTML), CTA só aceita links `http(s)`, `/` ou `#` (bloqueia `javascript:`), Esc/fundo/× fecham, respeita `prefers-reduced-motion`. Um pop-up por vez; reavalia a cada rota de SPA.
- A pré-visualização no app usa o MESMO renderizador do site, preso a uma "janela" falsa via `transform` (o `position:fixed` do widget fica relativo à caixa).

## D-058 — Pesquisas (fase 13.4)
- Entidade `survey`: até 15 perguntas (NPS 0–10, CSAT 1–5, CES 1–7, nota 1–5, escolha única/múltipla, texto livre), obrigatória ou não, com lógica simples por pergunta ("se nota ≥ 9 → fim", "se escolheu X → pergunta N", só para frente). Mesmo gatilho/frequência/segmentação dos pop-ups; renderizada pelo `engage.js` (agora 5,4 KB gzip) uma pergunta por vez, sem emojis (escalas numéricas com rótulos nas pontas, D-036).
- Respostas vão num evento `survey` ao concluir (ou parciais ao fechar); o relatório usa a última resposta de cada visitante. NPS = % promotores (9–10) − % detratores (0–6); CSAT = % de 4–5; palavras frequentes sem stopwords em português.

## D-059 — Recomendações (fase 13.5)
- Catálogo e sinais vêm do próprio site via snippet (`product`, `cart`, `purchase`) — sem integração de feed. Modelo pré-calculado e servido pela CDN (`<conta>.reco.json`): o site e a API pública não fazem consulta pesada por requisição. Recalculado de hora em hora (mesmo ciclo do bandit), ao publicar uma vitrine e sob demanda.
- Estratégias (código puro em `@abtest/shared/reco`, usado no navegador e na API): quem viu também viu (co-visualização por visitante), comprados juntos (mesma compra/visitante), upsell (mesma categoria, preço ≥ 5% maior), próxima melhor oferta (categoria favorita do visitante, itens ainda não vistos), em alta (7 dias), mais vendidos. Sempre completa com os mais vistos e nunca recomenda o próprio produto; grupos com mais de 50 itens (robôs) não entram na associação.
- Vitrine = entidade `reco` (estratégia, título, seletor + posição, quantidade, segmentação), renderizada pelo `engage.js` em Shadow DOM, esperando o elemento aparecer (grades montadas depois do load). `engage.js` passou a 6,8 KB gzip (importa só o módulo de recomendação, não o zod).

## D-060 — Perfis e resolução de identidade (fase 14.1)
- Grafo de identidade determinístico: cada `identify` com `userId` liga aquele visitante (cookie de um navegador/dispositivo) ao usuário; o perfil de um usuário junta todos os visitantes ligados (cross-device, cross-browser), inclusive os eventos ANTES do login naquele dispositivo. Visitante ligado a dois usuários fica com o último. Sem identify, o perfil é o visitante anônimo. Nada de fingerprinting/probabilístico.
- Perfis calculados sob demanda a partir dos eventos do período (mesma linha do D-041): sessões, páginas, eventos, conversões, receita, atributos mesclados, experimentos vistos, dispositivos; busca por usuário/visitante/valor de atributo; resumo cross-device (identificados com 2+ dispositivos e combinações). A página do perfil mostra a linha do tempo de todos os dispositivos e as gravações (por visitante).

## D-061 — Segmentos do CDP e API de decisão (fase 14.2)
- Dois níveis de grupo, de propósito: **audiência** (D-055) é avaliada no navegador, na hora, com o que aquele navegador sabe — serve para segmentar o site sem atraso; **segmento do CDP** (`segment`) é avaliado no servidor sobre o perfil unificado (todos os dispositivos e todo o histórico do período): sessões, páginas, conversões, receita, eventos por nome, nº de dispositivos, recência, atributos, identificado, dispositivo usado, experimento/variação.
- Saídas: lista de membros (com link para o perfil), exportação CSV (com os atributos como colunas) e `GET /decide?user=|visitor=` — segmentos do perfil, variação de cada campanha server-side (mesmo bucketing do snippet, pela identidade mais estável: usuário > visitante) e próxima melhor oferta. É a peça da personalização cross-channel (e-mail, app, atendimento). Acesso por chave de API vem em 14.4.

## D-062 — Feature flags e SDK server-side (fase 14.3)
- Flag = entidade `flag` (chave, ligada, rollout %, regras de atributo, variáveis). A publicação grava `/cdn/<conta>.sdk.json` com as flags e as campanhas server-side em execução — separado da config do site (o navegador não precisa disso).
- `packages/sdk` (`@abtest/sdk`, ESM sem dependências; Node, Deno, Workers e navegador): baixa e recarrega a config a cada minuto e decide LOCALMENTE (sem ida à rede por decisão) com o mesmo murmurhash do snippet — o mesmo usuário cai na mesma variação no site e no backend. Rollout por usuário (`flag:<chave>`), regras de atributo (eq, ≠, em lista, contém, ≥, ≤). `getVariation` registra exposição (uma por usuário/processo) e `track` envia o evento e as conversões das metas customizadas, em lote, para o mesmo `/collect` — o relatório de experimento funciona igual.

## D-063 — Integrações (fase 14.4)
- **Chaves de API** (`abk_<conta>.<segredo>`): criadas só pelo owner e mostradas uma vez; o banco guarda só o SHA-256 (entidade `apikey`). Valem em `Authorization: Bearer` em qualquer rota, com papel viewer ou editor (nunca owner, nunca publicar JS). A conta vem do prefixo e a chave é conferida pelo hash dentro dela. Revogar apaga a entidade e a chave para na hora.
- **Webhooks** (entidade `webhook`): POST JSON por lote do `/collect`, só com os tipos assinados e sem eventos de QA, e um aviso a cada publicação. Assinatura `X-Abt-Signature: sha256=HMAC-SHA256(segredo, corpo)`; o segredo `whsec_…` é gerado pela API. Entrega "tentada uma vez", em segundo plano (`waitUntil` no Worker), sem fila nem retry. A lista fica em cache por 1 min por conta e é limpa a cada escrita de entidade. Botão de teste envia `type: 'test'`.
- **GA4 e GTM** (entidade `integrations`): vão na config publicada só quando ligados; o snippet (adapter do tracker) manda `experiment_impression` (evento recomendado do GA4) via `gtag` e `abt_exposure`/`abt_conversion` no `dataLayer`. Usa a tag que o site já tem; nada é carregado por nós.

## D-064 — Painel geral (fase 15.1)
- `GET /analytics/dashboard?days=` junta, numa leitura de eventos (período atual + anterior de mesma duração, sem `click`/`move`), os KPIs de todos os módulos reaproveitando os mesmos agregadores das telas (overview, pages, forms, engage, perfis, relatório de experimento). Assim os números do painel batem com os de cada módulo.
- Experimentos em execução aparecem com o líder na meta primária (maior P(melhor) entre os desafiantes), veredito, SRM e dias restantes. A tela é a primeira do menu ("Visão geral → Painel"); a lista de testes continua sendo a página inicial (`/`), para não mudar links existentes.

## D-065 — Insights automáticos (fase 15.2)
- Regras determinísticas sobre os mesmos agregadores das telas, não um modelo: cada achado tem número e link para a tela que o prova (relatório, mapa de calor, formulários, funil). Limiares em `LIMITS` (`apps/api/src/analytics/insights.ts`) para não gerar ruído: frustração ≥ 5% das visitas (mín. 50 visitas), scroll médio < 35%, campo responsável por ≥ 30% dos abandonos (mín. 10), passo de funil que perde ≥ 50% (mín. 30 visitantes), segmento divergente com P(> controle) ≥ 90% num dispositivo e ≤ 10% noutro (mín. 100 visitantes por variação em cada um).
- Ordem: crítico (SRM) → resultado (vencedora) → atenção → ideia. Gravidade sempre com ícone e rótulo, nunca só cor. Calculados a cada abertura do painel (sem tabela de "insights"): o achado some sozinho quando o problema some.

## D-066 — Analytics preditivo (fase 15.3)
- Regressão logística simples e explicável, não uma caixa-preta: 11 features que o snippet já tem no perfil local (páginas, sessões, dias desde a 1ª visita, páginas distintas, eventos, metas anteriores, celular, tablet, veio de outro site, veio de UTM, identificado), em escala log. O mesmo código (`@abtest/shared/predict`, sem zod) monta as features no navegador e no treino, então o score do site é o mesmo do treino.
- Treino na API (`apps/api/src/predict.ts`): um exemplo por página vista, com o perfil como o snippet o veria naquela hora; rótulo = fez a meta nos N dias seguintes (páginas sem a janela completa ficam de fora). Gradiente em lote com L2 sobre features padronizadas; os pesos voltam para a escala crua. 20% dos visitantes (hash) ficam de fora para medir AUC e conversão por decil. Mínimo de 20 visitantes na meta; até 20 mil exemplos (os mais recentes). Retreina de hora em hora (mesmo ciclo do bandit) e ao clicar em treinar; o modelo vai na config publicada (`propensity: { goal, w, b }`, ~150 bytes).
- No navegador o score entra no contexto das audiências (`score`), usado por testes, personalizações, pop-ups e pesquisas. Nada é enviado para calcular. Snippet: 9,6 KB gzip.

## D-067 — Otimização por IA e piloto automático (fase 15.4)
- `POST /ai/ideas`: o painel do período (D-064/D-065) reduzido a agregados — nenhum dado de visitante — vai para o Claude (`claude-opus-5-5`, esforço médio, saída estruturada por JSON Schema, `fallbacks: "default"` para recusas) e volta como até 6 ideias (hipótese, mudança, página, meta, impacto, esforço, dado que motivou). A resposta é validada com zod; recusa, corte ou erro caem nas regras. Sem `ANTHROPIC_API_KEY`, as ideias vêm de regras sobre os insights (uma por achado acionável), então a tela funciona em qualquer instalação.
- Helper `zodOutputFormat` do SDK exige zod ≥ 3.25 (o repo usa 3.24): usamos `betaJSONSchemaOutputFormat` com o schema escrito à mão e validamos com o nosso zod.
- Piloto automático = `allocation: 'autopilot'`: o bandit da fase 12.3, mais duas regras no rebalanceamento de hora em hora — variação com veredito "perdendo" vai a peso 0 e não volta; com vencedora declarada, só as vencedoras ficam com peso. Nunca zera todas. Quem já foi atribuído continua na sua variação (atribuição persistida).

## D-068 — Robustez: trava de clique na base e fuzz guiado pela especificação
- Clique duplo: a trava fica em `Button`/`Switch` (`usePending`): se o onClick devolve Promise, novos cliques são ignorados até ela terminar. Corrige todas as telas de uma vez; handler que quer a trava não pode descartar a Promise com `void`.
- Fuzz da API percorre `/openapi.json` (rotas novas entram sozinhas) e gera os dados de entidade/experimento a partir dos schemas zod; regra é "nunca 5xx" e o que foi aceito não pode quebrar leituras nem publicação.
- Byte nulo é recusado num middleware único (Postgres não aceita byte nulo em texto).
- IA: além do Claude, qualquer API compatível com OpenAI (`AI_BASE_URL`/`AI_MODEL`), para testes grátis; resposta validada pelo mesmo schema, falha cai nas regras.
- E2E: API sempre nova (`reuseExistingServer: false`) — robustez grava lixo e não pode atingir o banco de dev.

## D-069 — Consentimento LGPD/GDPR no snippet (fase 16.1)
- **Portão único** (`packages/snippet/src/consent.ts#consentGate`): o snippet inteiro (`boot` em main.ts) só liga com consentimento. Antes do aceite, nada de cookie de visitante, storage, testes, pop-ups, insights ou eventos. Não existe modo "testes sem cookie": sem id persistente o visitante trocaria de variação a cada página. Custo: na primeira página, o teste só entra depois do aceite (sem anti-flicker, a página aparece original e muda). Da segunda página em diante, a decisão salva liga o snippet na hora.
- **Decisão no cookie `_abt_c`** (1/0, 1 ano): único cookie gravado sem consentimento, pois guardar a recusa é necessário para respeitá-la. Recusa vale em qualquer conta (com ou sem espera): desliga na página (`rt.stop`, eventos descartados, gravação para de enviar via `InsightsBoot.stopped`) e apaga cookies e storage `_abt*`. Testes já aplicados na página são revertidos.
- **CMPs**: OneTrust (`OptanonActiveGroups` + `OneTrustGroupsUpdated`, padrão `C0002`), Cookiebot (`Cookiebot.consent[categoria]` + `CookiebotOnConsentReady`, padrão `statistics`), Google Consent Mode v2 (lê o `dataLayer` e embrulha `dataLayer.push`, padrão `analytics_storage`). No GCM, `default` negado é ignorado (só `update` decide; `default` concedido liga), senão quem já aceitou seria desligado e religado (perdendo o id) a cada página. O CMP só é lido com "esperar consentimento" ligado; sem espera, o site pode recusar por `abq`.
- **Config**: entidade `consent` (`ConsentSchema`); a config publicada ganha `consent: { cmp?, category? }` só quando exigido (ausente = roda direto).
- **Tamanho**: snippet 10.182 B gzip de 10.240 B. Trocar o alvo do esbuild de es2019 para es2020 (Safari 13.1+/Chrome 80+) liberaria ~440 B (`?.`/`??` deixam de ser transpilados); não feito aqui por mudar o suporte a navegadores antigos, fica para quando o espaço faltar.

## D-070 — Multi-conta, convites e conta nova (fase 16.2)
- **Pessoa × membro**: `users` é a pessoa (e-mail único, senha, conta padrão em `account_id`); papel e "publica JS" ficam em `memberships` (conta, pessoa). O JWT continua `{ sub, acc }`: o middleware carrega a pessoa *como membro da conta do token* (`repo.getUser(acc, id)` faz o join), então `User.accountId/role/canPublishJs` seguem valendo em todas as rotas e quem é removido perde o acesso na hora. Trocar de conta = novo token (`POST /accounts/:id/switch`), e o editor recarrega a página para nenhuma tela ficar com dado da conta anterior.
- **Login**: conta pedida (o editor manda a última usada) se for membro, senão a padrão, senão a mais antiga. Removido da conta padrão, a padrão passa para outra conta dele; sem nenhuma conta, a pessoa é apagada (não sobra login que não entra em nada).
- **Convite sem e-mail**: não há serviço de e-mail configurado, então `POST /invites` devolve o token uma vez e o owner copia o link (`?invite=inv_<conta>.<segredo>`) e manda por onde quiser. Só o hash fica guardado (entidade `invite`, mesmo padrão das chaves de API), vale 7 dias, é de uso único e um convite novo para o mesmo e-mail cancela o anterior. Quem já tem login precisa confirmar a senha (o link sozinho não põe ninguém numa conta); e-mail novo cria o login com nome e senha, sem verificação do e-mail: quem tem o link é tratado como dono do e-mail. Com serviço de e-mail, basta enviar o mesmo link.
- **Regras**: só owner convida, muda papel e remove; qualquer membro pode sair; a conta nunca fica sem owner (rebaixar ou remover o último owner → 400). Chave de API não é pessoa: não troca, não cria conta nem convida.
- **Conta nova**: qualquer pessoa logada cria (vira owner com "publica JS" e a conta já ganha o primeiro projeto com a URL do site). Sem cadastro público por enquanto (exigiria verificação de e-mail e limite contra abuso); fica para quando houver e-mail e cobrança.
- **Migração**: Postgres (drizzle 0007) e D1 (0007_memberships.sql) copiam o papel de cada usuário para `memberships` e removem `role`/`can_publish_js` de `users` (no SQLite o DROP COLUMN é permitido porque o CHECK é da própria coluna). Teste em `src/migrations-d1.test.ts`.

## D-071 — Histórico de atividades (fase 16.3)
- **Ponto único**: um middleware (`apps/api/src/audit.ts`, depois da autenticação) casa método + caminho numa tabela de regras e, se a resposta for 2xx, grava uma linha. As rotas não chamam nada; rota nova que muda configuração só precisa de uma linha na tabela. Para exclusões e mudanças de status a regra lê o alvo antes (nome e status anterior): PUT/PATCH de experimento ou PUT de entidade com `status` diferente vira iniciar/pausar/arquivar/voltar para rascunho, senão "editou". Falha na gravação só vai para o log, nunca derruba a requisição.
- **Fora de propósito**: login, troca de conta, sessão de edição, ideias da IA, treino do modelo, coleta do snippet e as ações automáticas do servidor (bandit/piloto automático). Registra o que pessoas (ou chaves de API, com o nome da chave e sem `userId`) mudaram.
- **Linha autossuficiente**: nome da pessoa e do alvo copiados na linha (sem FK para users), então o histórico continua legível depois que a pessoa sai ou o alvo é excluído. A tela de filtro por pessoa lista só os membros atuais.
- **Custo de escrita (D1 grátis, 100 mil linhas/dia)**: cada atividade = 3 linhas (tabela + 2 índices: `(account_id, created_at)` e `(account_id, target_id)`). Salvamentos seguidos do mesmo alvo pela mesma pessoa em até 10 min atualizam a linha anterior (2 linhas) em vez de inserir. No Worker a gravação vai para `waitUntil` (não atrasa a resposta); no Node é esperada (testes determinísticos).
- **Leitura**: qualquer papel (`GET /activities`, mais recentes primeiro, `next` = data da última linha para paginar). Sem expurgo: volume humano é pequeno; expurgar com o mesmo job de retenção se crescer.

## D-072 — Aprovação de publicação (fase 16.4)
- **Quem aprova**: owner ou membro com "publica JS" (`canPublishJs`), a mesma permissão de quem já podia publicar tudo; o rótulo na Equipe virou "publica JS e aprova". Sem permissão nova. Opção por conta em `accounts.require_approval` (coluna nos dois bancos; `PUT /account/settings` sem o campo mantém o valor, clientes antigos não desligam).
- **Portão no publicador, não só na rota**: com aprovação ligada e quem publica sem permissão, `publish.ts` compara a config nova com a última publicada (JSON com chaves ordenadas, porque o jsonb não guarda a ordem), ignorando versão, data, modelo preditivo e os pesos de experimentos com alocação automática, e incluindo flags/campanhas do SDK (lidas do `<conta>.sdk.json` na CDN). Diferente → `needsApproval`. Assim o bandit e o retreino (usuário de sistema sem permissão) continuam publicando sozinhos, mas não levam junto mudança pendente; e editor que republica o já aprovado não gera pedido à toa. Peso de experimento manual conta como mudança.
- **Pedido = entidade interna** `publish-request` (fora de `ENTITY_SCHEMAS`, então sem CRUD genérico; mesmo padrão de convites/chaves): sem tabela nova nem mudança de repo além da coluna. Um pendente por pessoa. `POST /publish` responde 202 `{ pending, requestId }`, então todas as telas que já publicavam viram pedido sem mudança de fluxo (só o texto do aviso).
- **Aprovar publica o estado atual**, não um retrato do momento do pedido (o app grava as mudanças direto, sem rascunho separado): quem aprova publica tudo o que está salvo e todos os pendentes são marcados como aprovados com a mesma versão. Publicação direta de quem aprova também resolve os pendentes. Recusa exige comentário. Corrida de dois aprovadores ao mesmo tempo publica duas vezes (inofensivo).
- **Notificação**: contador no menu (recarrega ao publicar/decidir e a cada minuto; para quem pediu, conta respostas posteriores à última visita, guardada no localStorage) e webhook `approval` com `{ status, request }` no pedido novo e em cada decisão. Sem e-mail (não há serviço configurado, ver D-070).
- **Auditoria**: regras novas no `audit.ts` (`request`, `approve` com versão e comentário, `reject` com comentário); o `POST /publish` com 202 vira "pediu aprovação".

## D-073 — Segurança de acesso: duas etapas, sessões e base de SSO (fase 16.5)
- **TOTP sem dependência**: RFC 6238/4226 com HMAC-SHA1 do Web Crypto (`apps/api/src/totp.ts`, vetores dos RFCs nos testes), roda no Worker e no Node. Segredo de 160 bits em base32, 6 dígitos, passo de 30 s, aceita ±1 passo; o último passo aceito fica gravado, então o mesmo código não vale duas vezes. Sem QR code: a tela mostra a chave e o link `otpauth://` (apps de senha e o celular abrem direto); gerar QR exigiria uma lib ou ~300 linhas de código próprio.
- **Estado por pessoa** em `users.mfa` (JSON: segredo, ativado, hashes SHA-256 dos códigos de recuperação, último passo, erros, bloqueio), não por conta: o login é da pessoa e vale em todas as contas dela. O segredo só sai da API em `POST /me/totp/setup`, antes de confirmado; depois nenhuma rota o devolve (`publicUser` não tem o campo). Segredo guardado em claro no banco, como o resto do estado de login: cifrar com chave derivada do `JWT_SECRET` amarraria o TOTP de todos a esse segredo (rotacionar = todos reconfiguram); fica para quando houver um cofre de chaves.
- **Login em duas fases**: senha certa + TOTP ligado → `{ mfa: 'totp', challenge }` (JWT de 5 min com `typ: 'mfa'` e sem `sid`, então não abre rota privada). `POST /auth/login/totp` confere código ou código de recuperação (uso único). 5 erros seguidos bloqueiam 15 min (429), contados na pessoa, então trocar de desafio não zera. Aceite de convite por quem já tem login com TOTP também pede o código (senão o link + senha pularia a 2ª etapa).
- **Exigência por conta** (`accounts.require_totp`, só owner e só quem já ativou o próprio): checada no middleware de autenticação a cada requisição (vem no mesmo join do `getUser`). Sem TOTP, a API responde 403 `code: 'totp_required'` em tudo menos `/me*`, `/sessions*` e troca de conta; o editor mostra só a tela de ativação (ou troca para outra conta / sai). Vale na hora para quem já está logado. Desativar o próprio TOTP é recusado enquanto a conta ativa exige. Chave de API não é pessoa: não é afetada.
- **Sessões revogáveis** aproveitando o recarregamento por requisição: tabela `user_sessions` (pessoa, conta ativa mais recente, user-agent, IP de `cf-connecting-ip`/`x-forwarded-for`, criada, vista por último, expira em 12 h) e o JWT carrega `sid`. Custo: +1 leitura por requisição e no máximo 1 escrita a cada 5 min por sessão (`SESSION_TOUCH_MS`); vencidas são apagadas quando a pessoa abre outra sessão. ## D-075 — Grupos mutuamente exclusivos (fase 17.1)
- **Entidade genérica** `group` (`GroupSchema`: descrição, `experiments: [{ id, percent }]`, `slots`), sem tabela nem migração: os dois repositórios já guardam entidades. A rota genérica ganha um passo só para `group` (`prepareGroup` em `routes/entities.ts`): experimentos precisam existir na conta e estar em um grupo só; as fatias mandadas pelo cliente são ignoradas e recalculadas. Duas gravações simultâneas podem pôr o mesmo teste em dois grupos; a publicação usa o primeiro (checagem sem transação; inofensivo).
- **Fatias estáveis**: o grupo é dividido em 100 fatias (1% cada) e guarda o dono de cada uma. `allocateSlots(anterior, novos)` mantém as fatias de cada teste (se diminuiu, perde as do fim), libera as de quem saiu e dá as livres de menor índice a quem cresceu ou entrou. Assim mudar o grupo só troca de teste os visitantes da diferença; nada é reembaralhado. Teste pausado/rascunho mantém a fatia (os visitantes dela ficam sem teste do grupo) até sair do grupo, para não mexer nos outros ao pausar.
- **Decisão no navegador com o mínimo de código**: a API compila em cada experimento publicado `group: { id, slots: number[] }` (sobrescrevendo sempre, então `group` nunca vem do cliente). O snippet só faz `slots.includes(bucketOf(visitante, idDoGrupo) % 100)`: mesmo hash do bucketing (MurmurHash3), com o id do grupo, então a fatia do visitante é a mesma para todos os testes do grupo e independente da escolha da variação dentro do teste. A checagem está em `chooseVariation`, então o SDK server-side e a decisão do CDP (`GET /decide`) dão o mesmo resultado do snippet sem código próprio; testes server-side e de navegador podem estar no mesmo grupo.
- **Exclusão vale mais que a persistência**: fora da fatia, `assign` apaga a atribuição guardada (`_abt_a`) e `assigned()` ignora o teste, então quem estava num teste antes do grupo (ou antes de uma mudança de fatias) deixa de vê-lo e de converter nele. QA (`?ab_force`) ignora o grupo.
- **Tráfego**: dentro da fatia valem a segmentação, as audiências e o tráfego do próprio teste (efetivo = fatia × tráfego); a tela mostra o efetivo quando o teste não está em 100%. Sobra (< 100%) = visitantes do grupo que não entram em nenhum (aviso na tela).
- **Orçamento do snippet**: +54 B gzip (10.182 → 10.236 B, limite 10.240 B); coube sem enxugar nem mudar o alvo es2019. A próxima mudança no runtime precisa da decisão do D-069 (es2020) ou de enxugar código.
- **Auditoria**: a regra genérica de entidades já registra criar/editar/excluir; só o rótulo "Grupos exclusivos" foi adicionado na tela de Atividades. Mudança de grupo também passa pela aprovação de publicação (D-072), porque muda a config publicada.

## D-079 — Teste sequencial, CUPED e metas de guarda (fase 17.5)
- **Opcional por experimento**: `stats: { sequential?, cuped?, guardrails?: goalId[] }` no experimento (coluna JSON `options`, sem migração nos dois bancos; dados antigos sem o campo = comportamento de antes, números idênticos). Não vai para a config publicada (removido em `publish.ts`): só o relatório usa.
- **Teste sequencial = mSPRT com mistura normal** (Johari, Koomen, Pekelis, Walsh, "Peeking at A/B tests", KDD 2017; "Always valid inference: continuous monitoring of A/B tests", Operations Research 2022 — o método do Stats Engine da Optimizely). Para a diferença das médias Δ̂ = B − A, V = s²A/nA + s²B/nB (normal, amostras grandes) e prior de mistura N(0, τ²): Λ = √(V/(V+τ²))·exp(τ²Δ̂²/(2V(V+τ²))); p sempre válido = min(1, 1/Λ) (desigualdade de Ville: P(algum dia 1/Λ ≤ α | H0) ≤ α); intervalo sempre válido Δ̂ ± √(V(V+τ²)/τ² · (2 ln(1/α) + ln((V+τ²)/V))). τ = 10% (o mesmo MDE da estimativa de duração) × |média do controle| (média combinada se o controle for 0). α = 5% bicaudal. Usamos o Λ do momento (não o mínimo histórico de p): é conservador e dispensa guardar estado — e o relatório tem período móvel, então "histórico" nem é bem definido. Intervalo da melhoria relativa = intervalo de Δ ÷ |média do controle| (aproximação: ignora a incerteza do denominador).
- **Verificação numérica** (`stats.test.ts`, semente fixa): 400 testes A/A com 20 olhadas de 500 visitantes por braço → falso positivo 0,5% com o sequencial (≤ α) contra 25,5% espiando o p-valor comum; com +20% de efeito real o sequencial detecta 93% (o comum, 99,5%). Mais conservador que o necessário em amostras pequenas, como esperado do mSPRT.
- **Veredito com sequencial**: vencedora/perdedora exigem p sempre válido < 5% (e o sinal do efeito) com o mínimo de 100 visitantes; "liderando" continua sendo P(> controle) ≥ 75% bayesiana (é só uma indicação). A chance bayesiana segue na tabela; a coluna p-valor vira "p sempre válido" e o intervalo da melhoria vira o sempre válido. Vale também para o piloto automático (lê o veredito), para os insights e para o painel.
- **CUPED** (Deng, Xu, Kohavi, Walker, WSDM 2013): Y' = Y − θ(X − X̄), θ = cov(X,Y)/var(X) com todos os visitantes juntos (sem viés porque X é anterior à exposição). **Covariável**: páginas vistas pelo visitante nos 30 dias antes da sua PRIMEIRA exposição a este teste (buscada também antes do período do relatório, para não contar atividade já sob efeito do teste em quem entrou antes do período), excluindo os 5 s antes dela (a página vista do próprio carregamento da exposição, cuja ordem com a exposição poderia depender da variação). Visitante sem histórico = 0: é um valor real (visitante novo), não dado faltando; se ninguém tem histórico, var(X) = 0 → θ = 0 e nada muda. Escolhemos páginas vistas porque é o único sinal pré-exposição que existe para todo visitante (conversões são gravadas por experimento e só depois da exposição). Com CUPED a estatística (intervalo, melhoria, chances bayesianas com posterior Normal, Welch, sequencial) usa o Y' ajustado; a taxa exibida continua a observada. O relatório mostra a redução de variância (= correlação²) por meta, na taxa e na receita.
- **Custo (Worker 10 ms)**: sequencial e guarda são O(1) por variação sobre o que já é calculado; CUPED é O(n) e custa uma consulta extra (páginas vistas e exposições dos visitantes do relatório desde 30 dias antes do período, a mesma usada pelo filtro de dispositivo, que agora aproveita a mesma leitura). Nada de simulação no request. Por isso CUPED só roda na rota do relatório: bandit/piloto automático, insights e painel continuam sem ele (decidem um pouco mais devagar, nunca com outro critério de viés). ponytail: a consulta respeita o teto de eventos (D-041); visitante com muitas páginas além do teto fica com X subcontado (sem viés entre variações, só menos redução).
- **Metas de guarda**: metas secundárias marcadas como "guarda". Violação = veredito "perdendo" na taxa ou na receita por visitante da meta de guarda (mesmo critério do resto: bayesiano ≤ 5% ou sequencial p < 5%, com mínimo de visitantes). Efeitos: lista `guardrails` no relatório (alerta no topo, etiqueta na linha e na lista de metas); a variação não pode ser "vencedora" na primária (vira "liderando", então o insight de vencedor e o "pronto para decidir" não disparam); no **piloto automático** ela sai do ar como uma perdedora (mandar todo o tráfego para quem prejudica outra métrica é exatamente o que a guarda deve impedir); nos **insights** vira achado crítico com link para o relatório na meta. Bandit simples (sem piloto) não muda: continua só Thompson na primária.


## D-080 — Receita por canal: primeiro e último toque (fase 17.6)
- **Sem mudar o snippet**: tudo sai das páginas vistas já coletadas (`url` com `utm_*`/ids de clique e `referrer`, D-041). O perfil local (`_abt_p.t`) só guarda a 1ª visita no navegador e não vai ao servidor; não foi usado.
- **Canal** (`classify` em `apps/api/src/analytics/attribution.ts`), nesta ordem: (1) com UTM, pelo `utm_medium`: cpc/ppc/cpm/paid*/display/banner/retargeting/ads → **mídia paga**; email/newsletter (também no `utm_source`) → **e-mail**; social/social-media/sm (ou sem meio e `utm_source` de rede social) → **redes sociais**; organic → **busca orgânica**; referral → **referência**; outro → **outras campanhas (UTM)**. (2) Sem UTM, id de clique de anúncio (`gclid`, `gbraid`, `wbraid`, `dclid`, `msclkid`) → **mídia paga** (`fbclid` não: vem também em links orgânicos). (3) Pelo host do referrer: webmail (mail.google.com, outlook…) → e-mail; buscadores (google, bing, yahoo, duckduckgo, yandex, baidu, ecosia…) → busca orgânica; redes (facebook, instagram, t.co, x, linkedin, tiktok, youtube, whatsapp…) → redes sociais; outro site → referência. (4) Sem referrer, ou referrer do próprio site abrindo visita → **direto**. Origem = `utm_source`, ou google/bing do id de clique, ou host do referrer sem `www.`, ou "(direto)"; campanha = `utm_campaign` ou "(sem campanha)".
- **Toque** = 1ª página de cada visita (sessão do cookie, D-041; evento sem `sessionId`: 30 min sem páginas) ou página no meio da visita que chega com UTM/id de clique (campanha nova). Referrer externo no meio da visita **não** abre toque: a volta do gateway de pagamento não rouba a venda (sem lista de exclusão para manter).
- **Modelos**: crédito inteiro a um toque. **Primeiro toque** = primeira visita dentro da janela (pode ser direta). **Último toque** = última visita **não direta** antes da conversão (padrão de mercado, "last non-direct click"); só sem nenhuma visita com origem fica "direto". Conversão sem visita registrada na janela = direto. **Janela fixa de 30 dias** antes da conversão (as páginas vistas são lidas desde 30 dias antes do início do período).
- **O que é conversão**: no painel, eventos customizados (`abq.push(['track', nome, valor])`) com valor > 0 por padrão (as "compras"), ou um evento escolhido pelo nome (a resposta traz os nomes do período); conversões de experimento ficam de fora (repetiriam a mesma compra por teste). No relatório, os eventos `conversion` da meta escolhida (padrão a primária), por variação. Cada evento conta (compra repetida conta duas vezes), diferente do relatório principal, que conta visitantes; a receita bate com a do relatório. QA nunca entra.
- **CPU (Worker 10 ms)**: rotas próprias, nunca dentro do `/analytics/dashboard`; o cartão do Painel e o do relatório (só ao clicar em "Ver por canal") buscam à parte. Duas leituras: eventos do período e páginas vistas dos visitantes que converteram (filtro por id até 400 visitantes = até 5 consultas no D1; acima disso, todas as páginas do intervalo numa consulta). Agregação O(conversões × toques do visitante). Mesmo teto de eventos por consulta (D-041). Sem consulta nova no repositório.
- **Fora de propósito**: modelos fracionados (linear, decaimento, data-driven), janela configurável, custo de mídia (ROAS) e o filtro de dispositivo do relatório no cartão por canal.


## D-081 — Variação por texto com IA (fase 18.1)
- **Fluxo**: agent `pageSummary` → app → `POST /ai/variation` (editor+) → modelo → API valida → app pré-visualiza → "Aplicar" adiciona à variação. O agent é quem lê o DOM (é o único com acesso ao iframe de outro origin); a API nunca vê seletores.
- **`ref` em vez de seletor**: o resumo identifica cada elemento por `e1`, `e2`… (ordem do documento) e o modelo só cita esses refs. Os alvos (seletor estável do `packages/selector` + alternativos + impressão digital) ficam com o app, que troca o ref pelo alvo. Assim o modelo não pode apontar para um elemento fora do resumo, gasta menos tokens e a checagem "seletor veio do resumo" vira "ref existe no resumo" (feita na API e de novo no app, que descarta ref que sumiu).
- **Resumo**: elementos visíveis (subárvore com `display:none` nem é visitada; `visibility:hidden` fica fora) que são títulos, links, botões, imagens, campos, labels, blocos (header/nav/main/section/footer/form/aside/article, com só o começo do texto) ou têm texto próprio. Por elemento: tag, texto (até 80; blocos até 60), id/class (3)/href/src/alt/placeholder/type/name/aria-label/role, cor, fundo, tamanho e peso da fonte. Limites: 200 elementos e 60 mil caracteres (o agent para antes; a API recusa acima com 413; o zod limita cada campo).
- **Alterações permitidas** (lista fechada, `AiChangeSchema`): `setText` (não em img/campos/blocos, até 500 caracteres), `setStyle` (propriedade kebab-case, valor sem `url(`, `expression(`, `javascript:`, `@import`, `!important`, `< > { } ; \`; várias propriedades do mesmo elemento viram uma alteração, até 12), `setAttribute` (só alt, title, placeholder, aria-label, href, target `_blank`/`_self`), `hide`, `replaceImage` (só em img) e `move` (âncora também do resumo). **Fora**: setHTML, insertHTML, addClass/removeClass, remove e qualquer CSS/JS custom: HTML e JS escritos pelo modelo a partir de texto não confiável seriam injeção de código no site do cliente. URLs (href, imagem) só se aparecem no pedido ou já estão na página (o modelo não inventa destino), e nunca `javascript:`/`data:`.
- **Injeção de prompt**: texto da página e pedido são dados, delimitados em `<pagina>` e `<pedido>`; o `<` do JSON da página vira `<` e as tags são tiradas do pedido, então nada fecha a delimitação. O sistema diz que o conteúdo é dado. O que segura de verdade é a validação: mesmo um modelo enganado só consegue propor alterações declarativas sobre elementos da página, e o usuário vê tudo antes de aplicar.
- **Provedor**: o mesmo das ideias (Claude `claude-opus-5-5` com saída estruturada e `effort: low`, senão o compatível com OpenAI com `json_object` + zod; `compatJson` foi extraído de `compatIdeas` e serve aos dois). Sem provedor = 409 com mensagem dizendo o que configurar (não há "regras" para isso: inventar alterações sem IA seria pior que avisar; 409 e não 503 porque a API nunca responde 5xx a entrada válida, ver fuzz). Falha do provedor = 502 com o motivo.
- **Pré-visualização**: a proposta vira operações com id `ai_N` aplicadas no iframe por cima da variação (`applyVariation` com a lista + propostas), sem entrar no estado. Trocar de página, variação ou modo descarta. "Aplicar" usa a ação nova `addOperations` (um passo só no desfazer, página do funil atual).
- **Auditoria**: gerar não grava atividade (não muda o que o site recebe, como as ideias); as alterações aplicadas entram na versão do experimento ao salvar, que já é auditada.


## D-082 — Ideia → teste em um clique (fase 18.2)
- **Criação na API** (`POST /ai/ideas/:id/experiment`), não no app: a API já tem a ideia, as metas da conta e o projeto, e é o único lugar onde dá para garantir idempotência. **Id do teste = `exp_<id da ideia>`** (chave também estável): repetir, clique duplo ou duas abas devolvem o mesmo teste (a rota procura o teste pelo vínculo e pelo id derivado antes de criar; duas requisições simultâneas gravam o mesmo id, a segunda vira uma versão do mesmo teste). No app, um ref impede o segundo pedido. Excluir o teste e clicar de novo (ideia reaberta) cria outro com o mesmo id.
- **Hipótese**: campo opcional `hypothesis` do experimento (até 2 mil caracteres) na coluna JSON `options`: sem migração nos dois bancos, dados salvos sem o campo continuam válidos. É da equipe: sai da config publicada e do link de pré-visualização. Editável em Configurações.
- **Página**: o 1º trecho do texto da ideia; caminho (`/carrinho`) ou URL do mesmo origin do projeto viram a página aberta no editor + regra de URL exata (com `*`, "contém" o prefixo). Qualquer outra coisa ("todo o site", "formulário", outro domínio, `javascript:`) abre a home do projeto sem regra de URL (vale no site todo; o usuário restringe). Usa o 1º projeto da conta (o mesmo que "Novo teste" usa); conta sem projeto = 409.
- **Meta**: as metas dos outros testes da conta são o "catálogo" (não há metas de conta). Casa a meta cuja chave (ou o evento, se customizada) tem todas as palavras no texto da meta da ideia (sem acento, sem palavras vazias, plural simples), a mais específica; copia a definição com id novo. Sem casamento, cria uma meta de evento customizado com o nome do texto (`conversao-pagina`) e o editor avisa para conferir se o site dispara esse evento. ponytail: casamento por palavras; sinônimos ("compra" × "pedido") não casam, o usuário troca em Configurações.
- **Alterações sugeridas**: reaproveita a 18.1 sem rota nova. A tela de ideias deixa no sessionStorage do navegador (chave por teste, lida e apagada ao abrir o editor) o título e a mudança da ideia; o editor abre na aba IA com o pedido preenchido e, se a resposta da criação disse que há IA, dispara a geração uma vez quando o site conecta e mostra a pré-visualização (aceitar ou descartar, nada entra na variação sem aceite). Sem IA, o texto fica como sugestão e o aviso explica. Antes de resumir a página, o painel espera até 3 s se o resumo vier vazio (SPA ainda montando logo depois da conexão). Só o teste recém-criado recebe a sugestão; abrir de novo não gera.
- **Vínculo e auditoria**: a ideia ganha `experimentId` e `doneAt` (vai para "Executadas", com "Abrir teste"; "Reabrir" mantém o vínculo). A criação entra no histórico como "criou experimento" com o detalhe "a partir de ideia da IA" (só quando cria de fato).

## D-083 — Backlog de hipóteses (fase 18.3)
- **Mesmas ideias, sem entidade paralela**: as ideias da IA (entidade `ai-ideas`, uma por conta) ganham `stage` (`idea` | `prioritized` | `testing` | `done`), `stageAt`, `ice` e, nas manuais, `source: 'manual'` e `createdBy`. Sem migração de banco nos dois repositórios. **Migração na leitura** (`migrate`): ideia sem `stage` com `doneAt` e teste ligado vira "em teste" (o status do teste decide o resto), com `doneAt` sem teste vira "concluída", sem `doneAt` vira "ideia"; a próxima escrita grava o formato novo. `PUT {done}` continua aceito (concluída/reaberta).
- **ICE**: impacto, confiança e facilidade, inteiros de 1 a 10; **score = (I + C + F) / 3**, arredondado a uma casa (`iceScore` em `packages/shared`, usado pela API e pela tela). Média e não produto: mesma escala das notas (1–10) e uma nota baixa não zera a ideia. Coluna ordenada por score (sem ICE no fim, mais nova primeiro). Facilidade em vez de esforço para que "maior = melhor" nas três. A tela sugere notas a partir das etiquetas da IA (alto 8, médio 5, baixo 3; facilidade = 11 − esforço), confiança 5.
- **Movimentos**: priorizar (salvar ICE) move "ideia" → "priorizada". "Em teste" exige teste ligado ("Criar teste" da 18.2 ou "Ligar a teste" a um existente da conta). **Com teste ligado (que existe), a coluna é derivada do status dele na resposta, não gravada**: arquivado = concluída; rascunho, no ar ou pausado = em teste; concluída à mão continua concluída. Assim desarquivar volta para "em teste" sem job nem gancho em todo lugar que muda status (rota, agendamento, piloto automático). Com teste ligado, voltar para ideia/priorizada é 409 (desligar o teste primeiro, que volta para "priorizada"). Teste excluído = a ideia volta a ser livre (mostra "teste ligado foi excluído").
- **Resultado** (`GET /ai/ideas/:id/result`): relatório do teste ligado (365 dias, mesma função do relatório, `loadReport`) resumido da meta primária: alguma variação com veredito "vencedora" = vencedora (a de maior lift); todas "perdedoras" = perdedora; senão inconclusivo (destaca a de maior lift). **Nunca no GET do quadro** (CPU do Worker grátis): cada cartão concluído com teste pede o seu, uma requisição por relatório. Guardado só quando o teste está arquivado (definitivo), numa entidade à parte por ideia (`idea-result`, `name` = id da ideia) para não reescrever a entidade das ideias a partir de um GET; desarquivado, o guardado é apagado. O quadro devolve o resultado guardado junto, então concluídas antigas não recalculam.
- **Auditoria**: criar, editar, priorizar (detalhe "ICE 7,7"), mover (detalhe = coluna de destino), ligar (detalhe = teste), desligar, descartar e limpar o backlog entram no histórico (alvo "Backlog de hipóteses"). Gerar com IA continua fora, e os movimentos automáticos não geram linha própria (a mudança de status do teste já é registrada).
- **Quadro**: colunas com `<section>` e cartões arrastáveis por HTML5 nativo; a alternativa por teclado é o `<select>` "Mover…" de cada cartão, que só lista os destinos válidos. Sem biblioteca de arrastar.
- ponytail: ler-modificar-gravar sem trava na entidade das ideias (como antes); duas pessoas movendo ideias no mesmo instante podem perder uma das mudanças.

## D-084 — Resumo por IA de gravação, mapa de calor e pesquisa (fase 18.4)
- **Uma rota, três entradas** (`POST /ai/summary`, `kind` = recording | heatmap | survey), todas montadas na API a partir do que já é coletado, compactas e agregadas: nunca o replay bruto, nunca valor digitado. Saídas em `packages/shared/src/ai-summary.ts` (zod): gravação = objetivo, passos, onde travou, frustração; mapa = atenção, ignorado, sugestões; pesquisa = sentimento geral, visão geral e temas (nome, contagem, sentimento, até 3 exemplos). A API corta textos (400) e listas (8) antes de validar e limita a contagem do tema ao tamanho da amostra.
- **Nome dos elementos**: na gravação, sai do próprio rrweb (snapshot completo de cada página + nós adicionados + textos alterados; ids recomeçam a cada snapshot), casando cada clique nosso com o clique do rrweb mais próximo (até 1,5 s); o nome vale também para os cliques de frustração do mesmo seletor. Texto de campo e `.abt-mask` já chegam mascarados da gravação. No mapa de calor os eventos só têm seletor: o editor pede ao agent (RPC novo `heatmapContext`, na página real do visualizador) o texto de cada seletor e os clicáveis visíveis que ninguém clicou (até 30), que é o que permite dizer "o que é ignorado". Sem agent, fica o último trecho do seletor.
- **Sem PII**: e-mails e sequências com 8+ dígitos (telefone, CPF, cartão, CEP) viram `[e-mail]`/`[número]` em tudo que vem do site ou do visitante (títulos, rótulos, nomes de campo, respostas) e de novo na resposta do modelo; URLs só com o caminho (query e hash fora). Preços e anos ficam (menos de 8 dígitos). ponytail: regex; nomes próprios e endereços escritos por extenso passam.
- **Pesquisa**: última resposta de cada visitante (sem QA), as 150 mais recentes (divididas entre as perguntas abertas), 300 caracteres cada, com a nota NPS/CSAT/CES/nota da mesma pessoa. O resumo avisa quando é amostra.
- **Injeção de prompt**: os dados vão num bloco `<dados>` com `<` escapado no JSON (nada fecha a tag) e o sistema diz que é dado. Pior caso de um modelo enganado é um texto ruim na tela: a saída é só texto (o React escapa), nada vira operação nem HTML.
- **Cache**: entidade genérica `ai-summary` (sem migração, mesmo contrato nos dois repositórios), `name` = alvo (`recording:<sessão>`, `heatmap:<página>|<dispositivo>|<teste>|<variação>`, `survey:<id>|<dias>`), com a impressão digital (SHA-256 da entrada + versão do prompt). Mesma impressão e menos de 7 dias = cache. Impressão diferente (dado novo) a menos de 1 h do último resumo = devolve o guardado com `stale` (a tela mostra "Há dados novos" e "Atualizar", que manda `refresh`); senão gera. Assim página movimentada não chama o modelo a cada clique. Até 50 resumos por conta (apaga os mais antigos). Quem só lê (viewer) recebe o guardado, mesmo desatualizado, mas não gera (403): gerar custa.
- **Sem IA**: a pesquisa cai num resumo por regras (barato, O(n) nas respostas da amostra): temas = palavras mais frequentes (em quantas respostas aparecem, sem palavras vazias), sentimento por palavras-chave com negação simples ("não demorou" = positivo) e, sem palavra-chave, pela nota da pessoa. Não vai para o cache (configurar a IA depois gera de verdade). Também é o plano B quando o provedor falha. Gravação e mapa sem IA = 409 dizendo o que configurar; provedor falhando = 502 (inventar "objetivo" ou "sugestões" por regra seria pior que avisar).
- **Worker**: chamada síncrona como a 18.1 (Claude com `effort: low` e 4 mil tokens, ou o compatível com orçamento de 25 s): no Worker conta a CPU, não a espera do modelo, e nada roda em `waitUntil`. A CPU é a da montagem da entrada: a gravação lê os blocos do rrweb como o GET da gravação já faz; o mapa usa a mesma consulta do mapa (1 ponto por elemento) e os eventos de frustração da página.
- **Fora**: erros de JavaScript do site (não são coletados), resumo de várias gravações juntas, histórico de resumos.

## D-085 — Assistente de relatório (fase 18.5)
- **Mesma rota e cache da 18.4** (`POST /ai/summary`, `kind: 'report'`, entidade `ai-summary`, chave `report:<teste>|<dias>|<dispositivo>`, impressão digital da entrada, "Há dados novos" dentro de 1 h, 7 dias). Componente `AiSummaryCard` estendido (rótulo do botão e ações a partir do resultado).
- **Números vêm da tela, não recalculados** (CPU do Worker grátis: o relatório roda Monte Carlo e já foi calculado para a tela). A tela manda o relatório que recebeu (`ReportNumbersSchema` em packages/shared; série, seções, nomes e chaves descartados ou trocados pelos do experimento). A API **confere** antes de usar: variações e metas iguais às do experimento e na ordem dele, conversões ≤ visitantes, taxa = conversões/visitantes, soma dos visitantes, só o controle com veredito "base", metas de guarda do próprio teste; senão 409 "recarregue". Não dá para provar que a estatística não foi editada (só recalculando), e **não precisa**: os números só viram texto para quem já pode ver o relatório, nada é decidido nem publicado a partir deles; o botão de ação só abre o editor ou cria uma ideia, sempre por clique. ponytail: um editor que forje números coerentes consegue gravar uma explicação errada no cache, que outros veem até os números mudarem; recalcular no servidor resolve se virar problema.
- **Regras decidem, a IA explica**: ação (investigar SRM > implementar a vencedora de maior melhoria > parar e iterar se todas perdem ou pioram meta de guarda > testar ideia mais ousada se a amostra necessária foi atingida sem decisão > continuar rodando com os dias restantes do relatório), variação, dias, confiança (alta/média/baixa: SRM ou amostra < 100 = baixa; menos de 7 dias de dados ou qualquer ressalva rebaixa) e ressalvas (SRM, amostra pequena, meta de guarda, meta secundária piorando, menos de 7 dias = efeito novidade/ciclo semanal) são das regras e vão na entrada como `recommendation`. O modelo escreve só resumo, negócio, ressalvas, texto do próximo passo e ideia; a API sobrescreve ação/confiança/variação/dias com as das regras, usa as ressalvas do modelo só se forem pelo menos tantas quanto as das regras, e a ideia só quando a ação é iterar.
- **Números citados conferidos**: todo número do texto da IA precisa existir na entrada (inclusive dentro da hipótese e dos nomes), lido no formato brasileiro (1.234,5), com tolerância de arredondamento (inteiro ±0,5, decimal ±0,051); inteiros até 10 e 95, 99, 100, 1.000, 0,05 e 5 passam. Número fora = resposta rejeitada → explicação por regras com o motivo na nota. Limite: confere que o número existe, não que foi usado no lugar certo; a entrada já traz as contas prontas (conversões a cada 1.000 visitantes, % formatados) para a IA não precisar calcular.
- **Sem IA: explicação por regras** (template determinístico a partir do veredito, com os mesmos números formatados), sempre disponível e sem custo: sem chave, provedor falhando, número inventado e para quem só lê sem explicação guardada (viewer não gera com IA, mas recebe as regras em vez de 403; só no relatório, a pesquisa segue como na 18.4). Não vai para o cache.
- **Entrada**: experimento, hipótese (18.2), status, período, dias com dados (da série), dispositivo, método (bayesiano ou sequencial, com os limiares), CUPED, por variação visitantes/conversões/taxa/intervalo/melhoria e intervalo (sempre válido com sequencial)/chance de vencer/chance de ser a melhor/p/veredito/meta de guarda/receita por visitante, até 5 metas secundárias, SRM, violações de guarda, amostra necessária, dias restantes e melhoria detectável. Nomes e hipótese passam pela máscara de PII; dados delimitados em `<dados>` como na 18.4.
- **Ações**: implementar → "Abrir <variação> no editor" (pesos e publicação ficam com a pessoa); parar e iterar / testar ideia → "Criar ideia no backlog" (ideia manual da 18.3 com título, hipótese, mudança, página do teste e meta primária). Investigar SRM e continuar rodando não têm botão. Só para editor/owner.
- `maskPii`/`clean` foram para `apps/api/src/pii.ts` (reexportados por ai-summary.ts) para ai-report.ts não importar ai-summary.ts em círculo.

## D-086 — Geração de ideias em passos no Worker grátis (fase 18.6)
- **Escolha: máquina de estados persistida avançada pelo cliente** (cada `POST /ai/ideas/step` faz um passo numa requisição própria). Avaliadas e descartadas: Worker chamando a si mesmo (fetch para o próprio workers.dev não é permitido; precisaria de service binding para si e de rota interna com segredo), Cloudflare Queues (disponibilidade no plano grátis não confirmada) e Durable Objects com alarme (no plano grátis desde 2025-04, só com SQLite). Todas exigem peças que não existem no Node (self-host); o passo pedido pela tela é igual nos dois ambientes, não tem rota interna para proteger (a rota é autenticada e a conta vem do token) e não depende de `waitUntil` (usado só para o passo terminar se a pessoa fechar a tela no meio).
- **Estado** (entidade `ai-ideas-job`, uma por conta, separada das ideias): `running` com passo `dashboard` → `model` → `done`/`error`; guarda período, início, vez (`leaseUntil`), tentativas, a entrada compacta do modelo e as ideias por regras (calculadas no passo do painel: o plano B não recalcula nada). Separada para que mover/editar ideias durante a geração não desfaça o estado dela.
- **Idempotência**: cada passo pega a vez com `swapEntity` (UPDATE … WHERE updated_at = lido; a nova versão é sempre maior que a anterior), nos dois repositórios. Quem perde devolve o estado na hora. Iniciar também usa a troca (dois "Gerar" = uma geração); duas entidades criadas na primeira vez simultânea são reduzidas à mais recente na leitura.
- **Falhas**: vez do painel 15 s, do modelo 90 s (Claude com timeout de 60 s, compatível com 25 s). Vez vencida sem terminar = invocação morta (no Worker grátis, quase sempre os 10 ms de CPU do painel). Painel: 2 tentativas (exceção solta a vez na hora e guarda o motivo); depois o modelo recebe só nome e status dos testes e a tela diz que o painel estava indisponível. Sem IA e sem painel = erro (as regras dependem dos achados do painel). Modelo: uma tentativa; erro ou morte = regras do painel, com o motivo na tela. Geração sem avanço há 10 min expira (aparece como erro; "Gerar" começa outra).
- **Quem avança**: qualquer papel com a tela aberta (o passo só continua o que um editor iniciou e não cria custo novo); iniciar segue exigindo editor. Sair da tela pausa; voltar continua.
- ponytail: as ideias são gravadas antes de marcar "pronto"; se outra chamada tomar a vez depois dos 90 s, os dois lotes podem entrar (título repetido não entra de novo).

## D-087 — Link de pré-visualização sem resposta não encerra a sessão; keep-alive da API acima do padrão
- **Problema** (E2E instável na suíte completa, `preview-link.spec.ts`): o preview.js tratava qualquer falha do `fetch` do rascunho (sair da página no meio da busca, rede, API fora do ar) como link expirado e apagava `_abt_preview` da sessão. Quem navegava antes da resposta (no teste, `goBack` logo após abrir /produto.html com a API lenta) saía do modo pré-visualização com o link ainda válido.
- **Escolha**: só a resposta da API (não-2xx) encerra a sessão e mostra "expirado ou revogado". Sem resposta, a página fica original sem selo e a próxima página tenta de novo.
- **Keep-alive**: o servidor Node da API (`server.ts`) passou a manter conexões ociosas por 65 s (padrão do Node: 5 s; `headersTimeout` 66 s). Cliente com keep-alive que reusa o socket no instante em que o servidor fecha recebia ECONNRESET em POST (visto no E2E: o agent do Playwright reusa sockets entre testes sem tempo de ociosidade). 65 s fica acima do ocioso típico de balanceadores (60 s). Worker não muda.


## D-088 — Mensagens de limite do plano grátis (versão de testes)
- Enquanto a produção roda no plano grátis da Cloudflare, quem testa precisa distinguir "limite do servidor" de "erro do app".
- Estouro de CPU (10 ms): a Cloudflare encerra o Worker e responde 503 sem CORS, que o navegador vê como "Failed to fetch". O editor sonda `GET /health` com `mode: 'no-cors'` (resposta opaca basta): se a API responde, mostra "Limite da versão de testes…" (sugere período menor); se não, "Sem conexão com a API". Não dá para saber com certeza que foi CPU, mas com a API viva é a causa conhecida.
- Cotas diárias (D1 linhas, KV escritas): `app.onError` reconhece a mensagem da cota e responde 503 `{ code: 'plan_limit' }` com CORS; o editor mostra "Limite diário da versão de testes…" (renova 00:00 UTC). ## D-090 — SDKs server-side em Python, PHP, Go e Java/Kotlin (fase 19.2)
- **Mesma API e semântica do SDK JS**, no idioma de cada linguagem (`is_enabled`/`isEnabled`/`IsEnabled`, `get_variables`, `get_variation`, `track`, `flush`, `close`, `version`), só stdlib: Python 3.10+ (urllib, threads daemon), PHP 8.1+ de 64 bits (cURL se houver, senão streams), Go 1.21+ (net/http, goroutines, `atomic.Pointer`), Java 11+ (`java.net.http`, `ScheduledExecutorService` daemon). Config em `sdks/` fora dos workspaces do pnpm (não são pacotes JS).
- **Kotlin = SDK Java**: a API Java (classes finais, `AutoCloseable`, `Map`, `Double` anulável) já é idiomática o bastante no Kotlin (`use {}`, `mapOf`, `v?.key`); um módulo Kotlin próprio exigiria Gradle/kotlinc e uma segunda implementação do hash sem ganho real. Exemplo de Kotlin no README e numa aba da tela.
- **Compatibilidade por vetores, não por reimplementação conferida a olho**: o SDK TS é a referência; `packages/sdk/src/vectors.test.ts` gera `sdks/test-vectors.json` com `toMatchFileSnapshot` (localmente grava se for novo e falha se mudou; no CI nunca grava). Mudança proposital no bucketing ou nas regras: `pnpm --filter @abtest/sdk vectors` e os quatro SDKs precisam acompanhar. `packages/sdk/turbo.json` põe o arquivo nas entradas do cache do `test`. `sdks/` fica fora do Prettier.
- **Aritmética de 32 bits sem sinal** (o ponto em que cada linguagem erra diferente): Python mascara com `& 0xffffffff` depois de cada multiplicação/rotação; Go usa `uint32` (multiplicação já dá a volta, `bits.RotateLeft32`); Java usa `int` (multiplicação módulo 2^32 = `Math.imul`), `>>>` em todo deslocamento à direita, `& 0xff` em cada byte (byte do Java tem sinal) e devolve `long` sem sinal; PHP mantém tudo em [0, 2^32) num int de 64 bits e multiplica em duas metades de 16 bits (`mul32`), porque `0xffffffff * 0xcc9e2d51` passa de 2^63 e o PHP viraria float, perdendo precisão (fórmula conferida contra a multiplicação exata em 200 mil pares). UTF-8: Python e Java trocam surrogate solto por U+FFFD como o `TextEncoder` (Java codifica à mão por code point; `getBytes` usaria `?`); Go e PHP já recebem bytes (string inválida em UTF-8 não existe do lado do JS).
- **Arredondamentos e números do JS**: `Math.round` (meio para cima) reimplementado em todas (o `round` do Python é bancário; o do PHP afasta do zero). A conta da variação repete a mesma sequência de operações em double (`b / included * total`, subtrações), então dá o mesmo resultado bit a bit. Regras: `String(v)` de número usa os dígitos mais curtos no formato do JS (expoente a partir de 1e21 e abaixo de 1e-6; Python via `repr`, Go `FormatFloat(-1)`, Java pelo menor `BigDecimal` que volta ao mesmo double, porque o `Double.toString` só é o mais curto a partir do JDK 19; PHP pelo menor `sprintf('%.Ne')`, sem depender do `serialize_precision`); inteiro acima de 2^53 é formatado como o double que o JS teria. `Number(v)`: só dígitos ASCII (o `float()` do Python aceita dígitos Unicode e `1_000`), vazio = 0, `0x/0o/0b`, `Infinity` com sinal, resto NaN. `trim` com o conjunto exato do JS (o `strip()` do Python também tira U+0085 e U+001C–U+001F). ponytail: no PHP, `0x...` com mais de 53 bits acumula em float (pode diferir do JS no último bit); nas outras, conversão exata.
- **PHP é por requisição**: o sdk.json vai para um arquivo de cache compartilhado (`cacheFile`, padrão no temp; escrita atômica com rename) válido por `refreshMs`; se a CDN falhar, vale o cache vencido. Em processo longo (Swoole/RoadRunner/fila) o cliente recarrega sozinho quando a validade passa. Eventos saem no fim da requisição (`register_shutdown_function`) ou em `flush()`. Config passada nas opções não recarrega.
- **Igual ao SDK JS de propósito** (para não divergir): erro de rede no carregamento mantém a última config (sem config = tudo desligado/nulo); falha de rede no envio devolve os eventos para a fila, resposta HTTP de erro descarta; exposição uma vez por usuário e campanha por processo; `props` vazio ainda é enviado. Atributo `None`/`null`/`nil` conta como ausente (só `neq` passa). Go: intervalos `0` = padrão e negativo = nunca (o zero do Go não pode significar "nunca" como no JS).
- **Testes sem framework** nas linguagens em que o framework seria dependência: Python `unittest`, Go `testing`, PHP script com `exit(1)` (avisos viram falha), Java `main` (Maven só compila: `-DskipTests package`, que ainda compila os testes). CI em `.github/workflows/sdks.yml` (ubuntu-24.04; matrizes Python 3.10/3.13, PHP 8.1/8.4, Go 1.21/1.24 com `gofmt`, `vet` e `-race`, Java 11/21) disparado por mudanças em `sdks/`, `packages/sdk`, `packages/shared/src` e no bucketing do snippet.
- **Instalação pelo repositório** (pip via git, Composer com repositório vcs, `go get` do subdiretório, `mvn install`): publicar em PyPI/Packagist/Maven Central fica para quando houver nome e conta da empresa.

## D-097 — Vencedor só com amostra planejada e semana completa; melhoria observada (fase 20.2)
- **Trava única** em `experimentReport` (`canDecide`/`gateVerdict` em `packages/shared/src/stats.ts`): vencedora ou perdedora só quando a menor variação atinge a amostra planejada daquela meta (+10% sobre a taxa do controle, α 0,05, poder 0,8) e o teste tem 7 dias completos desde a primeira exposição. Exceção: teste sequencial (mSPRT), válido a qualquer momento. Antes disso vencedora vira "liderando" e perdedora "inconclusivo". Todo consumidor herda (rodapé, insights do painel, piloto automático, resultado da ideia, assistente); o assistente confere de novo com os números do cliente. Efeito colateral aceito: alertas de guarda sem sequencial e corte do piloto automático também esperam a maturidade.
- Relatório ganha `maturity: { ready, daysRunning, minDays, progress }`; tela mostra "Dados insuficientes, ainda coletando" e a barra de progresso.
- **Melhoria (`lift`) = observada** (taxa variação ÷ controle − 1); intervalo de 95% continua bayesiano como rótulo secundário. Cartão da meta: "conversão: +x% · receita: +y%".
- **Duração**: `remainingDuration` (`packages/shared/src/duration.ts`, teto `MAX_USEFUL_DAYS = 56`). Acima de 8 semanas: aviso para encerrar ou redesenhar; o assistente recomenda `test-idea` em vez de "continuar por N dias".
- **Teste que não é rascunho abre no relatório**; editar teste no ar mostra aviso com "Criar nova versão" (duplica como rascunho, contagem do zero). Não existe "reiniciar contagem".
- Lista: tráfego efetivo (tráfego × fatia do grupo exclusivo), aba "Ativos", "Novo experimento" abre "Novo experimento", eyebrow "Insights" em Funis/Coortes/Jornadas.

## D-098 — Página normalizada única, mapa de calor que acompanha o DOM, filtros de domínio, período e variação (fase 20.3)
- **Página**: `normalizePage` (API) é a única regra: origin + caminho, sem query, hash, barra final, `/index.html` nem `.html`/`.htm`. Postgres usa a mesma regex via `pageSql`; D1 grava a coluna `page` com a função e a migração D1 0013 regrava os eventos antigos (custa escritas da cota do D1 grátis: aplicar num dia sem seed). Funil: destinos de quem desiste usam só o caminho (`pagePath`). Não ignora maiúsculas (`.HTML`).
- **Domínios antigos**: filtro escolhido pelo usuário (chips em Mapas de calor e Gravações), lembrado no `localStorage` (`abt.hiddenDomains`); sem configuração por conta (esconder no navegador não perde dados).
- **Mapa no celular vazio** (causa): desenho único; no celular o menu fica `display:none` e o carrossel esconde slides inativos, então quem desenhava com outro slide ativo via "4 elementos inexistentes" e nunca redesenhava. Agora um MutationObserver redesenha (no máximo a cada 200 ms) e o agent avisa o app por `heatmapStatus {resolved, missing}`.
- **Animações**: enquanto o mapa está aberto, `<style data-abt-heatmap>` leva animações e transições ao estado final (`animation-play-state: paused` congelaria slide que entra com fade). Timers de carrossel JS não são parados; o desenho por elemento acompanha.
- **Variação**: seletor de experimento/variação no visualizador; a variação é aplicada no iframe (operações e CSS, nunca JS) para os seletores baterem com o que o visitante viu.
- **Período**: `days` opcional em `/heatmap` (sem ele, todo o histórico); o detalhe herda o período da lista.
- **Gravações**: domínio por linha, amostragem do workspace no topo, mínimo de 10 s por padrão ("Qualquer duração" mostra as de 0:00).

## D-100 — Controles técnicos de conformidade (fase 20.6)
- **Cabeçalhos**: API com `secureHeaders` (HSTS 1 ano + subdomínios, nosniff, `Referrer-Policy: no-referrer`, XFO DENY, `frame-ancestors 'none'`) e CORP desligado, porque o snippet `/cdn/*` é carregado por `<script>` nos sites dos clientes. Editor e demo com `public/_headers`; CSP do editor só com scripts/workers da própria origem (Monaco vem do bundle), `frame-src https: blob:` e `connect-src 'self' <API>` (plugin do Vite troca `__API_ORIGIN__` pela origem de `VITE_API_URL`). Demo sem XFO (é o site em teste), `/bloqueado/*` mantém o DENY.

- **Direitos do titular**: `GET`/`DELETE /privacy/subject?visitorId=|userId=` (só owner; `userId` resolve visitantes pelos `identify`, teto `EVENT_LIMIT`); exporta eventos, perfis, pesquisas, formulários e gravações; apaga eventos, gravações e entregas de webhook. Dados já enviados a destinos externos (CRM, S3, BigQuery) ficam com o cliente.
- **CI**: `.github/workflows/security.yml` (`pnpm audit --prod --audit-level=high`, gitleaks, CodeQL) e `dependabot.yml`. drizzle-orm subiu para 0.45 (GHSA-gpj5-g38j-94v9); restam 2 moderadas do react-router 6 no demo.

## D-096 — Painel com agregados diários e blocos independentes (fase 20.1)
- **Agregados**: tabela `daily_stats(account_id, day, data)` (Drizzle 0013, D1 0014), uma linha por conta e dia UTC com totais somáveis (tráfego, dispositivos, rage/dead, 20 páginas mais vistas + 5 mais frustrantes com soma/contagem de scroll, formulários, pop-ups/pesquisas). Sobrevive ao expurgo dos eventos. Únicos do período não somam por dia: `COUNT(DISTINCT)` no banco, sem QA.
- **Preenchimento**: dia vira linha 1 h depois de terminar; hoje é sempre cru. Job de hora em hora faz 4 dias por conta (do mais recente para trás, até 180 dias); a leitura calcula até 16 dias faltantes e grava os fechados. Dia que falta conta zero e vai em `pendingDays`; com dia faltando no período anterior, variações ficam nulas. Backfill sem script (~45 h pelo cron).
- **Blocos**: `GET /analytics/dashboard/{summary|experiments|insights|profiles}`, cada um com sua cota de CPU; o editor mostra cada bloco ao chegar e "Não carregou. Tentar de novo" só no que falhou. `/analytics/dashboard` inteiro continua para as ideias de IA. Achados usam no máximo os últimos 7 dias crus.
- **Editor**: período padrão 7 dias; `ToastProvider` não abre aviso repetido com o mesmo texto (causa do aviso duplicado no celular) e junta os "Tentar de novo". Duração restante acima de 8 semanas mostra "não espere concluir; encerre ou redesenhe". Insight do funil: "A maioria sai do site."
- ponytail: scroll médio e pior página aproximados em sites com muitas URLs; evento que chega > 1 h após o fim do dia fica fora da linha; bloco de testes ainda lê exposições/conversões do período (agregado por teste/variação/dia se estourar); perfis em lotes de 80 visitantes (D1 grátis: 50 consultas por invocação).

## D-099 — Privacidade por padrão, URL alvo restrita, sessão em cookie, snippet com cache longo e acesso self-service (fase 20.4)
- **Consentimento**: `ConsentSchema.required` tem padrão `true`; conta sem escolha salva publica esperando consentimento, e a Instalação mostra "Escolha pendente" até salvar. Seed grava ligado em `demo` e `fluxo` só se não houver escolha (migra bancos antigos ao subir). Sites do demo têm banner (`apps/demo/public/consent.js`) que chama `abq.push(['consent', …])`. E2E sobe a API com `DEMO_CONSENT=0` (fixtures sem banner). Runtime do snippet inalterado.
- **URL alvo** (`packages/shared/src/target-url.ts`): só http/https, host de um projeto (ou subdomínio) ou localhost; dado pessoal por nome de parâmetro ou valor (e-mail, CPF/telefone formatados; só dígitos não conta, para não barrar ids). API recusa (400) ao criar, salvar, duplicar e restaurar; troca de status não valida (permite arquivar antigos). Editor tira os parâmetros e avisa.
- **Sessão**: JWT em cookie httpOnly `abt_session` (HTTPS: `SameSite=None; Secure; Partitioned`, porque o editor também roda em `*.workers.dev`; dev: Lax). CSRF: header `x-requested-with` (força preflight, só `EDITOR_ORIGINS`) + Origin conferido nas escritas por cookie. Bearer continua para API/SDK/testes (sem o header, token no corpo). SSO troca o `#sso=` pelo cookie em `POST /auth/cookie`.
- **CDN**: `/cdn/*` com `max-age=300, stale-while-revalidate=86400, stale-if-error=604800` (publicação chega em até ~5 min; substitui o `max-age=60` do D-008). Instalação oferece modo assíncrono com página escondida por no máximo 2,5 s.
- **Cadastro e senha**: `/auth/signup` (pessoa + workspace owner + projeto); `/auth/password/forgot` com resposta sempre igual; `/auth/password/reset` com JWT de 30 min ligado a hash do hash da senha (uso único, sem tabela), encerra todas as sessões. Senha mínima 10 caracteres; limite por IP com o limitador do login-guard. E-mail via `SendMail`; sem provedor, vai para o log. Limite conhecido: cadastro revela e-mail existente (409) até haver confirmação por e-mail.
